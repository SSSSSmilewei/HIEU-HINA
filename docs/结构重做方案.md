## 0. 原则

1. **四大块 + 底座**：签到、学习、通知与活动、排行；账号、成员、设置、门面、App 归入底座。（分类见 `docs/重构交接.md` §2）
2. **对外的接口路径不变**：手机 App（包括还在用的旧版）直接调用 `/api/...`，路径一改就坏。代码可以随便挪，路由表保持原样；要删的接口改成返回空数据或明确的提示，不直接删掉。
3. **数据库只做加法**：沿用 `src/worker/db.ts` 的版本迁移，新增 v13 起的迁移；不删表、不删列，旧数据保留。
4. **分阶段，每阶段一个 PR**，推到开发分支，负责人确认后再合并。每个阶段结束都要跑 `npm test`、`npx tsc --noEmit -p .`、`npm run build`。
5. **一次只做一类事**：搬代码的那次只搬不改行为；改行为的那次不搬代码。出问题时容易查。

## 4. 数据和权限结构：内外两套账号

### 4.1 现状
- 账号有 `users.kind`：`campus`（校内，学号登录，能签到）/ `external`（校外，用户名或邮箱登录，不签到，看不到成员真名）。
- 账号有 `users.role`：成员 / 管理员。
- 内容（公告、比赛、课程、知识块）**没有可见范围**，所有人看到的都一样。

### 4.2 建议的模型
把"是不是协会内部的人"做成一个**独立的标记**，和"校内 / 校外"分开：

| 维度 | 字段 | 含义 | 决定什么 |
|---|---|---|---|
| 身份 | `users.kind`（已有） | 校内 / 校外 | 用什么登录、能不能签到 |
| 归属 | `users.inner`（新，0 / 1） | 是不是协会内部成员 | 能不能看到"仅内部"的内容 |
| 权限 | `users.role`（已有） | 成员 / 管理员 | 能不能进后台 |

这样"校外的协会成员"（比如外校合作的同学）和"校内但不是协会成员"的同学都能表达。

内容加一个**可见范围** `audience`：`public`（所有人，包括游客）/ `member`（登录用户）/ `inner`（仅内部）。
- 公告和比赛：`notices` 表加 `audience` 列（v13，默认 `public`，旧公告不受影响）；后台发公告时多一个"谁能看到"的选项。
- 课程：课程包格式 `hiana-course@1` 加一个可选字段 `audience`（不写就是 `public`），改完要跑 `npx tsx scripts/schema.ts` 重新生成 JSON Schema；管理员发布的课程包同理。
- 知识块：同课程，`hiana-block@1` 加可选 `audience`。
- **过滤必须在服务器上做**：`GET /api/notices`、`/api/courses`、`/api/packages/:slug`、`/data/...` 等按当前用户过滤，不能只在页面上藏起来。静态的课程 JSON（构建产物）里仅内部的课程不能放进公开目录。

谁来打"内部"标记（❓ 选一种或都要）：
- A. 管理员在后台「成员 → 编辑」里勾选；
- B. 新增"内部"类型的邀请码，用它注册的账号自动带标记；
- C. 两者都有（AI 建议：B 管新人，A 管已有账号）。

❓ 还需要负责人确认：
- 现有的校内账号默认算不算内部？（AI 建议：迁移时把现有校内账号全部标为内部，校外账号不标，负责人再手动调整）
- 内部 / 非内部在签到、排行上有没有区别（比如排行榜只排内部成员）？
- 非内部的人点到仅内部内容的链接时，提示"仅协会成员可见"还是直接当作不存在（404）？
