## 一、新系统建设（2026-11-24 讨论，全部先记录，未开工）

**完整讨论记录见 [`docs/新系统建设.md`](新系统建设.md)**（2026-11-24 至 11-25：负责人的想法、AI 描述的想象、现有基础、待确认问题），接着讨论从那份文档入手。

负责人对平台下一步的核心想法：在系统里完成「看视频 → 记笔记 → 做作业 → 攒成自己的仓库」的完整闭环，而不是放链接和刷题。

### 1. 站内看视频
- 视频直接在系统里播放，接 B 站视频源（或其他视频源），不跳外站。
- 看视频的同时能在同屏看课堂教材（讲义），视频和教材互相配合。
- 与已有结论一致：视频不自托管，嵌入外站（灵感备忘录第五节）。

### 2. 笔记与语音输入
- 看视频时随时记笔记；在教材（讲义）里也能记笔记。
- 笔记支持语音输入；语音的识别、整理交给 AI 处理。
- 待细化：语音走浏览器识别还是识别 API；笔记和现有「蓝色钉子 · 标记」的关系（标记已经是段落上的私有笔记，要考虑复用还是分开）。

### 3. 系统级 AI 模块
- 把 AI 做成系统里统一的模块，接各种 API 来支撑各类功能（语音整理、笔记整理、以后的评语等），不是本地 AI。
- 现状：AI 只用于蓝色钉子「请 AI 回答」（智谱 GLM-4-Flash，`AI_API_KEY` 还没填）。要扩成通用模块。

### 4. 作业界面：coding + 个人仓库（替代现有刷题模式）
- 负责人明确否定现有练手题模式：不做学习通式的刷题，现有刷题内容也很差，这个方向要重做。
- 看完一节视频课 / 做完作业后，进入类 LeetCode、头歌（Educoder）的 coding 界面学习，带 Codédex 式的闯关元素。
- 做题内容优先用课程官方作业（如 CS61A 的 Python 作业），在系统里完成；官方没有的，由我们自己编写（2026-11-25 负责人确认）。
- **界面本质是 IDE，但用户看到的是独属于自己的仓库**：做题时定位到仓库里的某个文件夹，让同学有「在我的仓库里工作」的概念；做完的代码最终成为这个仓库的一部分，做题过程只是内嵌进了系统。
- 与已有规划的衔接：Forgejo 个人作业仓库正好承载「我的仓库」；浏览器判题（Pyodide 等）可支撑 Python 作业，正式判题用测试用例（官方测试改编，或我们自己编写），AI 只写评语和提示（调研-Codedex.md 第七节的结论）。
- 待细化：每生一个仓库还是每课一个仓库；仓库在 Forgejo 上的自动创建；作业提交、多次提交、成绩记录。

### 5. 游戏化界面交互（附加点，先记录）
- 做一套像 Codédex（https://www.codedex.io）那样的游戏界面，用纯粹的游戏交互完成学习。
- **不是以课程为模块化，而是以游戏界面为模块化**，类似力扣的闯关模式。
- 已有调研：`docs/调研-Codedex.md`。注意其结论：学机制（经验值、徽章、闯关节奏），不照搬画面和课程内容；它与我们的差别是「练习互不相关」，我们要做到关卡累计成一个项目仓库。
- 待细化：游戏化界面和第 4 条作业界面、现有课程页的关系；美术工作量。

### 6. VSCode 插件（附加点，先记录）
- 把系统做成 VSCode 插件，在本地直接管理这些学习内容（作业、仓库、进度等）。
- 需要很细化才能做好，先只记方向。本质 = git 操作 + 调平台 API（灵感备忘录第二节第 3 条）。

### 7. 底层支撑：学校服务器、Forgejo、OJ（已有规划，服务于上面各条）
- 向学校申请服务器并摸底（配置、公网 IP / 域名、运维人、能否装 Docker）——一切的前提，见第二大块。
- Forgejo：先只当作业仓库用，替代 GitHub 组织；之后平台对接提交状态。
- 刷题系统（Hydro）企划：12 月第一版、向学校申请两台虚拟机等，见灵感备忘录第七节。注意与第 4 条的关系：负责人现在倾向判题做在课程作业界面里，Hydro 可缓一缓或只用来办比赛（灵感备忘录第八节 AI 的初步想法，待确认）。
- 后续路线：作业模式（测试用例 + 多次提交 + 成绩）→ 自动评测 + AI 打分 + 申诉 → 统一登录、热力图打通。
- 通用化（任何协会都能用）：一键部署、课程内容管理后台。
