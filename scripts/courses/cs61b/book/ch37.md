## 37.1 压缩入门

作为压缩的入门，来看看创建和解压一个 zip 文件的过程。

```bash
$ zip mobydick.zip mobydick.txt 
adding: mobydick.txt (deflated 59%)

$ ls -l
-rw-rw-r-- 1 jug jug 643207 Apr 24 10:55 mobydick.txt
-rw-rw-r-- 1 jug jug 261375 Apr 24 10:55 mobydick.zip
```

注意，压缩前后文件的大小变了！

### 压缩模型一：作用在比特上的算法

在第一个压缩模型里，我们把压缩看作对一串比特应用一个*压缩算法*。要撤销压缩，就应用对应的逆运算，即*解压算法*。

<figure><img src="../.gitbook/assets/image (25).png" alt=""><figcaption><p>压缩与解压。</p></figcaption></figure>

比如你有一个叫 `example.txt` 的文本文件。如果把这个文本文件压缩，会得到 `example.zip`，一个比原来的 `example.txt` 小得多的 zip 文件。这就是压缩背后的主要思想——一种用来减小文件大小的技术。

然后，如果把 `example.zip` 解压成一个叫 `unzippedexample.txt` 的文件，你会发现 `example.txt` 和 `unzippedexample.txt` 没有任何区别。这说明是**无损**（lossless）压缩，没有丢失任何信息。

## 37.2 前缀码

想想 Java 里怎样表示英文文本。我们把文本表示成字符序列，每个字符占 8 比特的内存。

那么，一个简单的压缩办法就是每个字符用少于 8 比特。为此，我们得决定每个**符号**（symbol，即字符）配哪个**码字**（codeword，即比特序列）。

### 映射字母和数字符号

#### 摩尔斯电码

#### 前缀码

为了不依赖实时信息，另一种策略是使用**前缀码**（prefix-free code，也叫无前缀码）。在前缀码中，没有一个码字是另一个码字的前缀。在摩尔斯电码的例子里，就不会弄不清模式 – – • – – • 中的 – – 是表示 M，还是 G 的开头。

## 37.3 香农–范诺编码

香农–范诺编码（Shannon-Fano code）是根据一组符号（字符）及其概率构造前缀码的一种方法。主要思想是：我们希望越常用的字符前缀码越短，越不常用的字符编码越长。

算法是：

* 统计文本中所有字符的相对频率。
* 分成频率大致相等的「左半」和「右半」。
  * 左半的码字前面加 0，右半加 1。
  * 重复。

最后会得到下面这样一棵树，频率较高的字符路径较短，频率较低的字符路径较长。

## 37.4 霍夫曼编码的概念

### 核心思想

霍夫曼编码（Huffman coding）用自底向上的方式构造前缀码，与香农–范诺编码自顶向下的方式相反。算法如下：

* 计算相对频率。
  * 把每个符号分配给一个节点，权重 = 相对频率。
  * 取两个最小的节点，把它们合并成一个超级节点，权重等于两者权重之和。
  * 重复，直到所有东西都成为一棵树的一部分。

### 数据结构

现在来想想，在霍夫曼编码的编码和解码过程中会用到哪些数据结构。回想一下，编码是把符号翻译成码字，解码则相反。例子如下：

* 编码把 `I ATE` 翻译成 `0000011000100101`。
* 解码把 `0000011000100101` 翻译成 `I ATE`。

1. **HashMap / TreeMap**：建一个从字符到比特序列的映射，调用 `get()` 方法查找每个字符。

区别是什么？数组比映射快，但如果有很多下标用不到，可能会用更多的内存。

### 实践中

既然已经讲了霍夫曼编码是什么，我们来谈谈想用它时会遇到的一些实际问题。可以采用两种主要的思路。

#### 语料库

* 对每种输入类型（英文文本、中文文本、图像），为每个类别收集大量的样本输入。用语料库为英文、中文等创建一套标准编码。
* 语料库（corpus）是作为一种语言的样本而使用的语言片段的集合。下面的例子中，我们指定用 `ENGLISH` 语料库来压缩 `mobydick.txt`。

```
$ java HuffmanEncodePh1 ENGLISH mobydick.txt
```

**问题：** 编码不是最优的，也就是说语料库和我们的输入并不完全吻合。在这个例子的语境下，这意味着 `mobydick.txt` 可能和 `ENGLISH` 文本的一般频率不太吻合，而可能有作者的一些别的特点或特别之处。

#### 专用编码

* 对每个可能的输入文件，专门为那个文件创建一套编码。这样，有人收到那个文件时，就能用我们随压缩文件一起发送的编码来解码。
* 如下面的例子所示，我们没有指定语料库，而是另外发送一个文件，帮助那个特定文件的解码过程。

```
$ java HuffmanEncodePh2 mobydick.txt
```

**问题：** 这种做法要求在压缩后的比特流里为码字表多占一些空间。不过，它一般比语料库的思路效果更好，所以在现实中常用。

## 37.5 压缩理论

### 压缩比

* 数据压缩的目标是在尽量保留信息的同时，减小一串数据的大小。例如，字母 `e` 在英语词典中比 `z` 出现得更频繁，所以我们希望用更少的比特表示 `e`。
* **压缩比**（compression ratio）衡量压缩后的数据大小和原始数据相差多少。
  * **霍夫曼编码**是一种用较少的比特表示常见符号的压缩技术，能得到更高效的编码。
  * **游程编码**（run-length encoding）是另一种压缩技术，它把重复出现的字符替换成这个字符本身加上它连续出现的次数。
  * **LZW** 是一种在输入中寻找常见的重复模式、并把它们替换成更短的编码的压缩技术。
* 大多数压缩技术背后的一般思想，是利用序列中已有的冗余或规律来减小数据的大小。不过，如果一个序列没有任何冗余或规律，可能就无法压缩。

### 自解压比特

* 自解压比特（self-extracting bits）是一种把压缩后的比特和解压算法包装成**一个比特序列**的压缩技术。
* 目标是把两个步骤合二为一，从而简化压缩和解压的过程。自解压比特可以用来创建可执行文件，在任何装有解释器（例如 Java 解释器）的系统上运行。

<figure><img src="../.gitbook/assets/Screenshot 2023-04-24 at 9.34.44 PM.png" alt=""><figcaption></figcaption></figure>

### HugPlant 的例子

* 要压缩 `hugplant.bmp` 这样的图像文件，可以把它切成 8 比特的块，对每个块做霍夫曼编码。
* 把压缩后的数据加上解码器，打包成一个自解压的 `.java` 文件，数据表示成一个 `byte[]` 数组。
* 把这个 `byte[]` 数组交给解释器时，解释器执行霍夫曼解码算法，得到原来的 `hugplant.bmp` 图像文件。
* 压缩后的比特流和霍夫曼解码算法加起来，比原来的图像文件**更小**，存储和传输起来更高效。
* 不过，压缩文件的接收者必须有合适的解释器，才能解码并重建原来的图像。

## 37.6 LZW 压缩

### 关键思想

LZW 方法基于这样的想法：利用输入数据中的冗余和模式来实现压缩。基本上，每个码字可以表示多个符号。

例如，想象一个符号序列 `ABCABCA`。在传统的压缩中，每个符号会被映射成一个定长的码字，得到类似 `010001001000100100` 这样的压缩序列。用 LZW 方法，码字可以基于输入数据中的模式。在这个例子里，算法一开始可能有一张码字表（A --> 0，B --> 1，C --> 2）。这可能得到看起来像 `01201201` 这样的压缩序列。通过允许码字表示多个符号，LZW 方法能比传统方法实现更高效的压缩。

（译注：原文这里把 LZW 误写成了「LWZ」，译文统一改为 LZW；后面的 Lempel、Ziv、Welch 也说明了正确的顺序。另外这个例子不太准确：`01201201` 仍然是每个符号一个码字，并没有体现「一个码字表示多个符号」。按 LZW，`ABCABCA` 会输出 A、B、C、AB、CA 五个码字，新加入码字表的 AB、BC、CA、ABC 等就是表示多个符号的码字。）

### 算法

* 算法一开始有一张简单的码字表，每个码字对应一个符号。
* 每用一次码字，就把上一个码字和下一个符号拼起来，创建一个新的码字。
* 算法没有规定码字表满了时怎么办，不过这个算法有很多变体，以不同的方式处理这个问题。
* LZW 方法的一个妙处是：只凭压缩后的比特流就能重建码字表，不需要把码字表和压缩数据一起发送。
* LZW 解压的 [演示](https://docs.google.com/presentation/d/1U8XO6CWfcU4QgrFOZmGjAgmaKxLc8HXk6qB1JQVlqrg/edit#slide=id.g53705ba95_0259)。

### 趣闻

* 这个算法以它的发明者 Lempel、Ziv 和 Welch 命名。
* LZW 算法被用作许多压缩工具的组成部分，包括 .gif 文件、.zip 文件等等。
* LZW 算法曾因有人试图收取专利许可费而饱受争议，不过这项专利在 2003 年到期了。

## 37.7 小结

**压缩模型一：作用在比特上的算法。** 给定一串比特 B，把它交给压缩算法 C，得到新的比特流 C(B)。可以把 C(B) 交给对应的解压算法来恢复 B。理想情况下，C(B) 比 B 小。

**变长码字。** 基本思想：用变长的码字表示符号，越常见的符号码字越短。例如，不必用 8 比特的 ASCII 值表示每个英文字符，可以用更短的序列表示更常见的值。摩尔斯电码就是变长码字系统的一个例子。

**前缀码。** 如果有的码字是别的码字的前缀，就会有歧义，就像在摩尔斯电码中看到的那样。前缀码是一种没有一个码字是另一个码字的前缀的编码。前缀码可以被唯一地解码。

**香农–范诺编码。** 香农–范诺编码是一种生成前缀码的直观的过程。首先，统计所有符号出现的次数。然后根据频率一次又一次地递归地把字符分成两半，每一半在码字末尾加一个 1 或 0。

**霍夫曼编码。** 霍夫曼编码生成一个可以证明是最优的前缀码，不像香农–范诺编码那样可能不是最优的。首先，统计所有符号出现的次数，为每个符号创建一个「节点」。然后把出现次数最少的两个节点合并成一棵以新的超级节点为根的树，每一半在码字开头加一个 1 或 0。重复这个过程，直到所有符号都成为树的一部分。得到的编码是最优的。

**霍夫曼编码的实现。** 要压缩一个符号序列，先统计频率，构建一个编码数组和一棵解码字典树，把字典树写到输出里，然后在编码数组里查找每个符号，把相应的比特序列写到输出里。要解压，先读入字典树，然后反复用最长前缀匹配恢复原来的符号。

**压缩背后的一般原理。** 霍夫曼编码的要旨是用较少的比特表示常见的符号。还有别的想法，比如游程编码，它把每个字符替换成它本身加上它连续出现的次数；还有 LZW，它在输入中寻找常见的重复模式。更一般地说，目标是利用输入中的冗余和已有的规律。

**通用压缩是不可能的。** 不可能有一个算法能把任何比特流都压缩 50%。否则，你可以反复压缩，直到最后只剩 1 个比特，这显然是荒谬的。第二个论证是：由于鸽巢原理，对于长度为（比如说）1000 的输入比特流，只有 1/2^499 能被压缩 50%。

**压缩模型二：自解压比特。** 把算法和输入比特流分开看待（就像在模型一中那样）是一个更准确的模型，但它似乎为一些奇怪的算法留下了余地，比如直接把想要的输出硬编码进算法本身。例如，我们可能有一个 .java 解压算法，里面有一个装着你最喜欢的电视剧的巨大的 `byte[]` 数组，如果算法收到输入 `010`，就输出这个 `byte[]` 数组。

换句话说，考虑输出的大小时，似乎更合理的做法是不仅算上压缩后的比特，还要算上用来解压的算法。

让这一点更具体的一个概念上的技巧是：把算法和比特本身想象成一个整体，可以把它看作一个自解压的比特序列。把这个自解压比特序列交给解释器，它会生成一个特定的输出序列。

**Hugplant 的例子。** 如果有一个图像文件，比如讲座中的 hugplant.bmp，可以把它切成 8 比特的块，然后做霍夫曼编码。如果把这个文件给别人，他们大概不知道怎样解压，因为霍夫曼编码不是主流操作系统支持的标准压缩算法。因此，我们还需要提供霍夫曼解码算法。可以把它作为一个单独的 .java 文件发送，但为了概念上的方便，也为了符合压缩模型二，我们设想把压缩后的比特流打包成 .java 文件里的一个 `byte[]` 数组。把它交给解释器时，这个比特流会生成原来的 hugplant.bmp，它的大小是压缩后的比特流加上霍夫曼解释器的 4 倍。

### 元认知问题

1. 利用自解压比特的思想，为重复 1000 次的序列 `abdefg` 想出一种少于 2000 比特的编码。

<details>

<summary>第 1 题</summary>

自解压比特的思想包括编写能生成原来的未压缩序列的代码或解释器。可以用下面的代码做到：

```java
public class Sequence {
    public static void main(String[] args) {
        for (int i = 0; i < 1000; i++) {
            for (int j = 0; j < 8; j++) {
                System.out.print(String.format("%c", 'a' + j));
            }
        }
    }
}
```

这段代码正好用了 239 个字符，即 1912 比特。这展示了自解压比特模型的威力：和霍夫曼编码需要的 24000 比特比一比。

（译注：题面的 `abdefg` 是原文笔误，从代码看指的是上一题的序列；代码输出的是 `a` 到 `h` 这 8 个字母。）

</details>
