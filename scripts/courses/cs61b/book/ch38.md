## 38.1 压缩的模型

### 比较压缩算法

上一章我们看到了很多压缩方法。这引出一个有意思的问题：对给定的比特流，最好的压缩算法是什么？

例如，考虑用不同的压缩格式压缩《白鲸》（Moby Dick）的文本。在这个例子里，`bzip2` 的压缩效果最好。

<figure><img src="../.gitbook/assets/image (136).png" alt=""><figcaption><p>对 <code>mobydick.txt</code> 使用不同的压缩格式</p></figcaption></figure>

不过，有人可能会说，对 `mobydick.txt` 最好的压缩算法就是下面这样：

```
D(B):
    if input == 0:
        return "Call me Ishamel. ...."
    else:
        return the text as is
```

用它作为解压函数，我们能把整部《白鲸》压缩成一个比特！

然而，这种做法有个问题。如果把解压算法的代码也算作压缩模型的一部分（回想上一章的压缩模型二），我们会看到《白鲸》并没有被压缩成一个比特，实际上需要的比特比原文还*多*！

### 解压算法

说到底，压缩算法的目标是找到能生成想要的更长比特序列的短比特序列。正式地说，我们的问题如下：

* 给定一个比特序列 `B`，找一个更短的序列 `DA + C(B)`，把它交给解释器时会产生 `B`。`DA` 表示解压算法的比特，`C(B)` 表示 `B` 压缩后的版本。

<figure><img src="../.gitbook/assets/image (153).png" alt=""><figcaption><p>把我们的压缩模型应用于 <code>mobydick.txt</code>。</p></figcaption></figure>

### 改进压缩

回想上一章 `HugPlant` 的例子。用霍夫曼编码，能达到 25% 的压缩比。

然而，用另一种我们暂且称为 `MysteryX` 的算法，可以把 `HugPlant.bmp` 压缩到 29,432 比特！这达到了 0.35% 的压缩比。在长度为 $8,389,594$ 的 $2^{8389594}$ 种可能的比特流中，只有 $2^{8360151}$ 分之一能达到这样的压缩比。

<figure><img src="../.gitbook/assets/image (157).png" alt=""><figcaption><p>一个大幅胜过霍夫曼编码的神秘压缩算法。</p></figcaption></figure>

`MysteryX` 是什么？其实就是为生成这个 `.bmp` 文件而写的 Java 代码 `HugPlant.java`！回到自解压比特的模型，我们看到了代码和解释器在压缩中的威力。这引出两个有意思的问题：

* **可理解的压缩**：给定一个目标比特流 `B`，能不能写一个算法，输出有用的、可读的 Java 代码？
* **最优压缩**：给定一个目标比特流 `B`，能不能找到输出这个比特流的*最短*的程序？

## 38.2 最优压缩与柯尔莫哥洛夫复杂度

### 柯尔莫哥洛夫复杂度

我们把比特流 `B` 的**柯尔莫哥洛夫复杂度**（Kolmogorov complexity）定义为输出 `B` 的最短比特流 $C_B$（的长度）。设 *Java 柯尔莫哥洛夫复杂度* $K_J(B)$ 为生成 `B` 的最短 Java 程序（的长度）。

注意，对任何比特流 $B$，$K(B)$ 一定存在。不过，求出并证明 $K(B)$ 可能很难，甚至不可能。

#### 语言与复杂度

要注意的重要一点是，柯尔莫哥洛夫复杂度与语言无关。要在另一种语言里运行用一种语言写的任何程序，只需要写一个解释器。例如，如果我想运行一个不容易翻译成 Java 的 Python 程序，可以改为用 Java 写一个解释器，读入 Python 程序的文本并运行它。在这种情况下，$K_J(B) \leq K_P(B) + I$，其中 $I$ 是解释器的长度（一个常数）。

（译注：准确地说，柯尔莫哥洛夫复杂度在相差一个常数（即解释器长度 $I$）的意义下与语言无关，上面的不等式说的正是这一点。）

这揭示了关于柯尔莫哥洛夫复杂度的一个非常深刻的事实：无论选用哪种语言来写压缩算法，大多数比特流从根本上都是不可压缩的。

考虑一个 1,000,000 比特的比特流。在所有可能的压缩算法中，只有 $2^{4999999}$ 分之一的比特流有机会被压缩 50% 以上（压缩到 499,999 比特或更少）。

（译注：长度不超过 499,999 的比特串一共不到 $2^{500000}$ 个，所以这个比例应约为 $2^{500000}$ 分之一，原文的指数多写了一个 9。）

#### 不可计算性

关于柯尔莫哥洛夫复杂度的另一个重要事实是，它是不可计算的。这一事实的证明见 [这里](https://en.wikipedia.org/w/index.php?title=Kolmogorov_complexity#Uncomputability_of_Kolmogorov_complexity)。

在实践中，这意味着不可能写出一个「完美」（最优）的压缩算法，因为我们甚至算不出最短程序的长度！

## 38.3 有空间 / 时间限制的压缩

正如上一节所说，不可能写出用最少的比特输出某个比特流 $B$ 的「完美」压缩算法。

### 有空间限制的压缩

不过，有空间限制的压缩问题呢？在这个问题里，我们有两个输入：一个比特流 $B$ 和一个目标大小 $S$。目标是找到一个长度 $\leq S$ 的、输出 $B$ 的程序。

结果是，这个问题同样是不可计算的。如果它可计算，我们就可以简单地对 $S$ 的不同取值做二分查找，找出最优压缩程序的大小，而上一节已经说明这是不可能的。

### 有空间和时间限制的压缩

如果在上面的问题上再加一个约束：最多只能运行 $T$ 行字节码，又会怎样？

这看起来可能有违直觉，但这种问题其实是可解的。我们用下面的算法：

```
for length L = 1....S:
    for each possible program P of length L:
        while (P is running && !(B is outputted) && lines_executed < T):
            run the next line of P
```

这个算法的运行时间是 $O(T \cdot 2^S)$，最终它要么输出某个输出正确、并满足 $T$ 和 $S$ 限制的程序 `P`，要么报告不存在这样的程序。

### 高效的有限制压缩

上面的运行时间是 $S$ 的指数。于是我们可能会问，有没有可能*高效地*解决有空间和时间限制的压缩问题。我们会在下一节看到，这取决于我们怎样定义高效。

## 38.4 P = NP

### 归约

结果是，有空间和时间限制的压缩问题可以归约到 3SAT、独立集（INDSET）、最长路径（LONGESTPATH）以及许多其他难题。（这些归约的实际证明极其复杂，本教材省略。）

<figure><img src="../.gitbook/assets/image (155).png" alt=""><figcaption><p>有空间和时间限制的压缩问题可以用 LONGEST_PATH（最长路径）来解。</p></figcaption></figure>

有空间和时间限制的压缩之所以能转化成最长路径（或上面提到的任何其他问题），是因为所有这些问题都属于一个叫作 **NP** 的**复杂性类**（complexity class）。这类问题的一个性质是，任何 NP 问题都可以归约到任何 NP 完全问题，包括最长路径。

在后面的小节里，我们会简要介绍 P、NP 和复杂性类是什么。不过，这些话题大多远远超出了本教材和这门课的范围，最好去上高年级的算法课。

### P 与 NP

所有是非问题可以分成两个主要的类：

* P：能高效解决的问题。
* NP：解能被高效验证的问题。这意味着，给出问题的一个答案，你能高效地检查这个答案对不对。

P 中问题的例子（注意 P 是 NP 的子集）：

* 这个数组有序吗？
  * 可以用任何排序算法给数组排序来解决，并通过检查相邻元素是否递增来验证。
* 这个数组有重复元素吗？
  * 可以用两重 for 循环来解决，并用类似的方式验证。

NP 中问题的例子：

* 这个 3SAT 问题有解吗？
  * 为 3SAT 问题生成一个解很难，但给定一组符号到布尔值的赋值，只要把值代进去，检查等式是否被满足就行。
* 在图 G 中，是否存在一条从 s 到 t、权重 > k 的路径？
  * 为这个问题（本质上就是最长路径）生成一个解很难，但给定一条路径，你可以很容易地验证它是不是一条从 s 到 t 的合法路径、权重是否 > k。

不在 NP 中的问题的例子：

* 这是我下一步能走的最好的一步棋吗？
  * 除非把之后所有步的所有可能性都推演出来，否则没有高效的方法验证一步棋确实是最优的。
* 最长路径是什么？
  * 这不是一个是非问题。

### NP 完全性

NP 问题有一个出人意料的性质：每个 NP 问题都可以归约到每个 NP 完全问题。这种归约还是「高效」的，因为问题可以在多项式时间内完成转化（预处理和后处理）。

这也意味着，解决了任何一个 NP 完全问题，本质上就解决了 NP 中的所有问题。到今天为止，已知的 NP 完全问题有好几万个，但还没有一个被（高效地）解决。

<figure><img src="../.gitbook/assets/image (149).png" alt=""><figcaption><p>NP 完全问题与归约。</p></figcaption></figure>

### P = NP？

计算机科学中一个悬而未决的问题是 P 是否等于 NP；换句话说，所有解能被高效验证的问题（NP）是否也都能被高效解决（P）？

支持 P = NP 可能成立的一个理由是，检查一个答案总是高效的。那么，只要剪枝得当，我们能不能高效地锁定一个答案？

### 程序性问题

1. 某个 100 万比特的序列能被压缩到 900,000 比特或更少的概率是多少？

<details>

<summary>第 1 题</summary>

长度为 100 万的比特序列有 $2^{1000000}$ 个，但长度不超过 900,000 的比特序列只有 $2^0 + 2^1 + ... + 2^{899999} + 2^{900000} = 2(2^{900000}) - 1 \approx 2^{900001}$ 个。这意味着任何一个比特序列能被压缩到 900,000 比特或更少的概率是 $\frac{2^{900001}}{2^{1000000}} = \frac{1}{2^{99999}}$。
