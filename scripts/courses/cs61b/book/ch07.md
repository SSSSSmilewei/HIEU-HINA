### 朴素的调整大小的数组

**选做练习 2.5.3**：假设有一个 AList，处在下图所示的状态。如果调用 `addLast(11)` 会怎样？我们该怎样处理这个问题？

![dllist\_circular\_sentinel\_size\_2.png](https://joshhug.gitbooks.io/hug61b/content/chap2/fig25/full_naive_alist.png)

在 Java 里，答案是直接建一个足够大、能容纳新数据的新数组。例如，可以设想这样添加新元素：

```java
int[] a = new int[size + 1];
System.arraycopy(items, 0, a, 0, size);
a[size] = 11;
items = a;
size = size + 1;
```

创建新数组并把元素复制过去的过程，常被称为「调整大小」（resizing）。这个叫法有点名不副实，因为数组其实并没有改变大小，我们只是建了一个更大的**新**数组。

**练习 2.5.4**：试着实现能配合调整大小的数组工作的 `addLast(int i)` 方法。

### 分析朴素的调整大小的数组

上一节尝试的做法性能糟糕透顶。做一个简单的计算实验，调用 `addLast` 100,000 次，会看到 `SLList` 完成得快到根本没法计时。相比之下，我们基于数组的列表要花好几秒。

要理解为什么，考虑下面的练习：

**练习 2.5.5**：假设有一个大小为 100 的数组。如果调用 insertBack 两次，整个过程中一共要创建和填写多少个盒子？假设一个数组的最后一个引用一丢失就立刻进行垃圾回收，任一时刻最多一共有多少个盒子？

**练习 2.5.6**：从一个大小为 100 的数组开始，如果调用 `addLast` 1,000 次，大约要创建和填写多少个内存盒子？

创建所有这些内存盒子、再把内容重新复制过去是要花时间的。在下图里，我们画出了总时间随操作次数的变化，上面是 SLList，下面是朴素的基于数组的列表。SLList 呈一条直线，这意味着每次 `add` 操作，列表花的额外时间都一样。这说明每一次操作都只花常数时间！也可以这样想：图像是线性的，表明每次操作花常数时间，因为常数的积分是一条直线。

相比之下，朴素的数组列表呈一条抛物线，表明每次操作花线性时间，因为直线的积分是抛物线。这在现实中有重大影响。对插入 100,000 项，可以通过计算 N^2/N 的比值粗略估算慢多少。往基于数组的列表里插入 100,000 项要花 (100,000^2)/100,000，即 100,000 倍那么长的时间。这显然是不可接受的。

### 几何式调整大小

可以让数组的大小按乘法而不是加法增长，来解决性能问题。也就是说，不再是**加上**等于某个调整因子 `RFACTOR` 的内存盒子数：

```java
public void insertBack(int x) {
    if (size == items.length) {
           resize(size + RFACTOR);
    }
    items[size] = x;
    size += 1;
}
```

而是把盒子数**乘以** `RFACTOR` 来调整大小。

```java
public void insertBack(int x) {
    if (size == items.length) {
           resize(size * RFACTOR);
    }
    items[size] = x;
    size += 1;
}
```

重做之前的计算实验，会看到新的 `AList` 完成 100,000 次插入所花的时间少到我们根本察觉不到。为什么会这样，完整的分析留到本书最后一章。

### 内存性能

我们的 `AList` 差不多完成了，但还有一个大问题。假设插入 1,000,000,000 项，后来又删除了 990,000,000 项。这时我们只用到 10,000,000 个内存盒子，99% 完全闲置。

为了解决这个问题，也可以在数组看起来变空时把它缩小。具体地说，我们定义一个「使用率」R，等于列表的大小除以 `items` 数组的长度。例如，在下图中，使用率是 0.04。

![fig25/usage\_ratio.png](https://joshhug.gitbooks.io/hug61b/content/chap2/fig25/usage_ratio.png)

在典型的实现里，R 降到 0.25 以下时，就把数组的大小减半。

### 泛型 AList

和前面一样，我们可以修改 `AList`，让它能存放任何数据类型，而不只是整数。为此，我们再次在类中使用特殊的尖括号记法，并在适当的地方用任意的类型参数代替整数。例如，下面我们用 `Glorp` 作为类型参数。

有一个重要的语法差别：由于泛型实现方式上的一个隐晦问题，Java 不允许我们创建泛型对象的数组。也就是说，不能这样写：

```java
Glorp[] items = new Glorp[8];
```

而必须用下面这种别扭的写法：

```java
Glorp[] items = (Glorp []) new Object[8];
```

这会产生一条编译警告，但我们只能接受它。后面的章节会更详细地讨论这个问题。

我们做的另一个改动，是把「删除」的元素都置为 null。以前，我们没有理由把删除的元素清零；而对于泛型对象，我们确实要把指向所存对象的引用置为 null。这是为了避免「游荡」（loitering）。回想一下，Java 只在最后一个引用丢失时才销毁对象。如果不把引用置为 null，Java 就不会对已经加入列表的那些对象做垃圾回收。

这是一个微妙的性能 bug，除非你刻意去找，否则不太可能注意到，但在某些情况下可能造成严重的内存浪费。
