### 查找问题

为了引出这一节，我们来考虑**查找问题**（search problem）。在这个问题中，我们拿到一串数据，目标是取出感兴趣的信息。例如，一个允许用户在个人主页上发布内容的网站，可能只想把这些内容展示给好友。另一个例子是一个新的气象站收到来自几千个气象站的记录，想显示某个指定日期和时间的天气图。

这两个都是查找问题的例子，只是形式不同！到目前为止我们构建的数据结构，都是为了解决各种领域中的查找问题。

我们来回顾一下目前见过的数据结构：

| 名称 | 存储操作 | 主要的读取操作 | 按什么读取 |
| --- | --- | --- | --- |
| 列表（List） | `add(key)`、`insert(key, index)` | `get(index)` | 下标 |
| 映射（Map） | `put(key, value)` | `get(key)` | 键本身 |
| 集合（Set） | `add(key)` | `containsKey(key)` | 键本身 |
| 优先队列 | `add(key)` | `getSmallest()` | 键的顺序（从小到大） |
| 并查集 | `connect(int_a, int_b)` | `isConnected(int_a, int_b)` | 两个整数值 |

所有这些数据结构都用来解决查找问题的不同实例。根据感兴趣的数据需要怎样被读取，它们各有各的用途。

需要注意的重要一点是，这些都是**抽象**数据类型（ADT），也就是说，我们定义的是数据结构的行为，而不是实现。每种数据结构都有多种可能的实现，我们甚至可以在一种数据结构的实现中使用另一种数据结构！我们常常用这些 ADT 来构建更复杂的数据结构。

### 抽象

抽象（abstraction）的思想是只关心某样东西的行为，而不关心底层的实现。这个概念并没有你想象的那么陌生！我们在日常生活中不知不觉地就在运用抽象的原则。例如，使用键盘可以看作是对「往计算机里输入文字」的一种抽象。取决于哪家公司生产，键盘的电路可以有多种实现，但我们不操心底下发生了什么，只关心它能让我们往计算机里打字。

构建数据结构时，抽象常常是*分层*运用的。

实现优先队列时，我们可以选择用堆序树来存放优先队列的元素。我们不操心堆序树的实现——只关心堆序树提供了哪些方法。

同样，堆序树也不关心它底层实现中用到的树数据结构是怎样实现的。

最后，使用我们所创建的优先队列的人，同样不关心我们是怎样做出这个优先队列的。他们只关心我们的优先队列能高效地支持加入元素和返回最小元素。

总之，我们常常可以借助另一个 ADT 来理解一个 ADT。ADT 有多层抽象，每一层定义的行为都比前一层的概念更具体。

## 26.1 字典树入门

*要么做，要么不做，没有「试试」（Trie）。*

我们先来考虑对现有 HashMap 实现的一种可能的改进。

HashMap 已经快得惊人了。对我们的可调整大小的拉链法哈希表，`contains(x)` 方法的运行时间是 $\Theta (1)$（假设分布均匀），`add(x)` 方法的运行时间也是 $\Theta(1)$（假设分布均匀，并按均摊计算）。这一般已经是我们能做到的最好了，但如果对要存放的数据有一些额外的了解，我们还能更快。

#### 特殊情形一：以字符为键的映射

如果我们知道键*只*是 ASCII 字符，就可以不用通用的 HashMap，改用一个数组，数组的每个下标对应一个特定的 ASCII 字符：

```java
public class DataIndexedCharMap<V> {
    private V[] items;
    public DataIndexedCharMap(int R) {
        items = (V[]) new Object[R];
    }
    public void put(char c, V val) {
        items[c] = val;
    }
    public V get(char c) {
        return items[c];
    }
}
```

上面是一种以字符为键的映射的可能实现。R 表示可能的字符个数（例如 ASCII 是 128）。我们不再需要存放可能拖慢运行时间的桶（代价是多用一些内存）。我们知道数据会均匀分布。

#### 特殊情形二：以字符串为键的映射

假设我们知道键总是字符串。可以用一种叫作**字典树**（Trie）的特殊数据结构。这种数据结构把字符串的每个字母存成树中的一个节点。它在取单词、加单词以及一些特殊的字符串操作上性能都很好。

字典树有几个关键思想：

* 每个节点只存一个字母。

## 26.2 字典树的实现

*拿出上大学的劲头来试一试（Trie）。*

现在我们来一步步实现一个字典树。第一种做法的思路是：每个节点存一个字母、它的孩子以及一个颜色。因为我们知道每个节点的键是一个字符，就可以用前面定义的 `DataIndexedCharMap` 类来映射到一个节点的所有孩子。记住，每个节点的孩子数最多等于可能的字符个数。

```java
public class TrieSet {
   private static final int R = 128; // ASCII
   private Node root;    // root of trie

   private static class Node {
      private char ch;  
      private boolean isKey;   
      private DataIndexedCharMap next;

      private Node(char c, boolean blue, int R) {
         ch = c; 
         isKey = blue;
         next = new DataIndexedCharMap<Node>(R);
      }
   }
}
```

注意，如果树中的节点孩子都比较少，那么对任何一个节点来说，它的 DataIndexedCharMap 对象里大部分都是 null 值。对只有一个孩子的节点，我们会有 128 个链接，其中 127 个是 null，只用到 1 个。这意味着浪费了大量多余的空间！后面我们会探讨其他的表示方式。

由此我们可以得出另一个重要的观察：每个链接对应一个字符，当且仅当那个字符**存在**。因此，可以去掉 Node 的字符变量，改为根据它在父节点的 `DataIndexedCharMap` 中的位置来确定字符的值。

```java
public class TrieSet {
   private static final int R = 128; // ASCII
   private Node root;    // root of trie

   private static class Node {
      // no more 'ch' instance variable
      private boolean isKey;   
      private DataIndexedCharMap next;

      private Node(boolean blue, int R) {
         isKey = blue;
         next = new DataIndexedCharMap<Node>(R);
      }
   }
}
```

### 性能

给定一棵有 N 个键的字典树，映射（集合）操作的运行时间如下：

* `add`：$\Theta (1)$
* `contains`：$\Theta (1)$

为什么是这样？不管字典树里有多少项，运行时间总是*与*键的个数*无关*。在最坏情况下，我们也只沿着一个键的长度遍历，这和字典树里键的个数无关。因此，我们用一个更合适的量来分析运行时间：L，即要查找的键的长度：

* `add`：$\Theta (L)$
* `contains`：$\Theta (L)$

我们不必操心均摊的调整大小时间，也不必要求键分布均匀，就得到了常数的运行时间！唯一的问题是，正如上面提到的，目前的设计在内存上极其浪费，因为每个节点都为每一个字符存了一个数组项，即使那个字符并不存在。

### 改进：记录孩子

{% embed url="https://www.youtube.com/watch?ab_channel=JoshHug&v=NTdJQB8yr2I" %}

为了解决浪费空间的问题，我们来探讨两种可能的解决办法：

* *另一个想法 #1*：基于哈希表的字典树。它不会创建一个有 128 个位置的数组，而是初始化成默认大小，只在需要时根据负载因子调整数组的大小。
* *另一个想法 #2*：基于 BST 的字典树。同样，它只在需要时才创建指向孩子的指针，并把孩子存在 BST 里。我们得考虑在这棵 BST 里查找的运行时间，但这不是一个坏办法。

实现字典树时，我们必须选一种映射来指向孩子。映射是一个 ADT，所以还必须选择这个映射的底层实现。这再次提醒了我们什么？在各种实现和我们想要创建的 ADT 之间有一道**抽象**屏障。这道抽象屏障让我们在满足 ADT 的行为要求时，可以利用每种实现的长处。我们来看看各自的长处：

* DataIndexedCharMap
  * 空间：每个节点 128 个链接
  * 运行时间：$\Theta (1)$
* BST
  * 空间：每个节点 $C$ 个链接，其中 $C$ 是孩子的个数
  * 运行时间：$O(\log R)$，其中 $R$ 是字母表的大小
* 哈希表
  * 空间：每个节点 $C$ 个链接，其中 $C$ 是孩子的个数
  * 运行时间：$O(R)$，其中 $R$ 是字母表的大小

注意：BST 和哈希表中每个链接的成本更高；R 是一个固定的数（这意味着可以把这些运行时间看作常数）。

我们可以得出几点结论。（BST、哈希表与 DataIndexedCharMap 之间）在内存和效率上有一点权衡。字典树操作的运行时间仍然是常数，没有任何附加条件。字典树在一些特殊操作上尤其能大显身手。

## 26.3 字典树的字符串操作

*再试一次（Trie）。*

字典树让我们能以常数时间查找和插入，但它们并不总比 BST 和哈希表表现得好。对任何字符串，我们都得遍历每一个字符，而在 BST 和哈希表中，我们立即就能访问整个字符串。不过，在字符串操作这个特定的应用上，字典树*有用得多*。

字典树的主要吸引力在于能高效地支持特定的字符串操作，比如*前缀匹配*。你可以想象为什么字典树让这件事极其高效！比如说，我们想找 longestPrefixOf（最长前缀）。只需拿着要找的单词，逐个字符和字典树里的字符比较，直到走不下去为止。类似地，如果想求 keyWithPrefix（带某前缀的键），可以一直走到前缀的末尾，然后返回字典树里剩下的所有键。

我们试着定义一个方法 `collect`，返回字典树中所有的键。伪代码如下：

```
collect():
    Create an empty list of results x
    For character c in root.next.keys():
        Call colHelp(c, x, root.next.get(c))
    Return x

colHelp(String s, List<String> x, Node n):
    if n.isKey:
        x.add(s)
    For character c in n.next.keys():
        Call colHelp(s + c, x, n.next.get(c))
```

我们先在外层函数里初始化各个值，然后创建一个递归的辅助函数，在递归调用的过程中携带更多参数。只有当前字符串是一个键时才把它加进去；然后把字符拼接到当前正在遍历的字符串（路径）上，对下一个孩子调用辅助函数。

现在我们可以试着写方法 `keysWithPrefix`，返回所有包含作为参数传入的前缀的键。我们会大量借用上面的 collect 方法。

```
keysWithPrefix(String s):
    Find the end of the prefix, alpha
    Create an empty list x
    For character in alpha.next.keys():
        Call colHelp("sa" + c, x, alpha.next.get(c))
    Return x
```

（译注：伪代码中的 `"sa" + c` 是沿用了以「sa」为前缀的例子，一般情况应为 `s + c`；另外如果前缀本身就是一个键，也应先把它加进结果。）

### 自动补全

在任何搜索引擎（比如谷歌）里输入时，总会有对你接下来要输入的内容的建议。这极其有用、方便。比如说我们要搜「How are you doing」，只要在谷歌里输入「how are」，就会看到它建议的正是这个查询。

实现这一点的一种方法就是用字典树！我们会构建一个从字符串到值的映射。

* 值表示谷歌认为这个字符串有多重要（大概是出现频率）。
* 因为字符串共享节点，可以高效地存放几十亿个字符串，减少浪费的重复。
* 当用户输入一个查询时，可以调用方法 `keysWithPrefix(x)`，返回值最高的 10 个字符串。

这个系统的一个主要缺陷是，用户输入的字符串很短时会怎样。可以想象，带有这个输入前缀的键会有几百万个，而实际上我们只想要 10 个。这个问题的一个可能的解决办法是在每个节点里存放这个子串的最佳值。然后可以按最佳值的顺序考虑孩子。

另一种优化是合并冗余的节点。这会得到一棵「基数字典树」（radix trie），它的每个节点既可以存字符也可以存字符串。我们不深入讨论这个。

### 小结

了解你要存放的数据的类型，能让你在创建高效的数据结构时拥有强大的力量。具体到实现映射和集合，如果我们知道所有的键都是字符串，就可以用字典树：

* 从理论上说，字典树在查找和插入上的性能比哈希表或平衡搜索树更好。
* 字典树的每个节点怎样存放孩子，有多种实现，具体地说是三种。这三种都可以，但哈希表最自然。
  * *DataIndexedCharMap*（缺点：空间用得过多；优点：速度快）
  * *茂密的 BST*（缺点：查找孩子更慢；优点：节省空间）
  * *哈希表*（缺点：每个链接的成本更高；优点：节省空间）
* 字典树在实践中可能并不真的更快，但它支持其他实现不支持的特殊字符串操作。
  * 因为字典树是逐个字符存放的，`longestPrefixOf` 和 `keysWithPrefix` 很容易实现。
  * `keysWithPrefix` 让自动补全这样的算法成为可能，还可以借助优先队列来优化。

| 名称 | 键的类型 | get(x) | add(x) |
| --- | --- | --- | --- |
| 平衡 BST | 可比较的 | $\Theta (\log N)$ | $\Theta (\log N)$ |
| 可调整大小的拉链法哈希表 | 可哈希的 | $\Theta (1)^{\dagger}$ | $\Theta (1)^{*\dagger}$ |
| 以数据为下标的数组 | 字符 | $\Theta (1)$ | $\Theta (1)$ |
| 字典树（BST、哈希表、DataIndexedCharMap） | 字符串 | $\Theta (1)$ | $\Theta (1)$ |

\*：平均情况；$\dagger$：元素分布均匀。

## 26.4 小结

*查找问题*是存放一组对象、以便能快速取出它们（即怎样实现映射或集合）。我们尤其感兴趣的是按字母或数字查找。

### 术语

* 字符串键的长度通常用 L 表示。
* 字母表的大小通常用 R 表示。

### 字典树

要知道怎样在字典树里插入和查找一项。要知道字典树的节点通常不存字母，字母是隐含地存在边的链接上的。要知道存放这些链接有很多种方式，其中最快但最耗内存的方式是用一个大小为 R 的数组。我们把这样的字典树叫作 R 路字典树（R-way trie）。

**字典树的优点。** 字典树的查找时间非常快，因为我们只看要取出的数据中的那几个字符。不过，它的主要优点是能高效地支持其他映射或集合实现不支持的各种操作，包括：

* longestPrefixOf（最长前缀）
* prefixMatches（前缀匹配）
* 拼写检查

### 元认知问题

1. 比较往 LLRB、哈希表和 R 路字典树里插入一个单词时，最坏情况下需要的字符比较次数。设 $R$ 是字母表的大小，$N$ 是字典树里的项数，$L$ 是任何单词的最大长度。

<details>

<summary>第 1 题</summary>

**LLRB**：我们总是在 LLRB 的底部插入，所以要做 $\Theta(\log N)$ 次比较来确定新节点放在哪里。每次单词比较最多要做 $L$ 次字符比较。因此一共是 $\Theta(L \log N)$ 次比较。

**哈希表**：在最坏情况下，所有项都哈希到同一个桶。插入时，必须把这个单词和桶里所有其他单词比较是否相等。假设这个桶里有 $N$ 项，这要做 $\Theta(LN)$ 次比较。

**R 路字典树**：在最坏情况下，我们沿着或新建 $L$ 个节点一直到单词末尾。因此最多 $\Theta(L)$ 次比较。
