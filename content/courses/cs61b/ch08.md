## 8.1 通用性问题

回想上周我们创建的两个列表类：SLList 和 AList。看看它们的文档会发现，它们非常相似。事实上，它们所有的方法都一样！

假设想写一个 `WordUtils` 类，里面放一些可以对单词列表执行的函数，其中包括一个计算 SLList 中最长字符串的方法。

**练习 4.1.1**：试着自己写这个方法。方法接收一个字符串 SLList，返回列表中最长的字符串。

下面是我们想出的方法。

```java
public static String longest(SLList<String> list) {
    int maxDex = 0;
    for (int i = 0; i < list.size(); i += 1) {
        String longestString = list.get(maxDex);
        String thisString = list.get(i);
        if (thisString.length() > longestString.length()) {
            maxDex = i;
        }
    }
    return list.get(maxDex);
}
```

怎样让这个方法也能用于 AList？

我们真正要做的只是修改方法的签名：参数

```java
SLList<String> list
```

要改成

```java
AList<String> list
```

现在 `WordUtils` 类里有两个方法名完全相同的方法：

```java
public static String longest(SLList<String> list)
```

和

```java
public static String longest(AList<String> list)
```

这在 Java 里确实是允许的！这叫作*方法重载*（method overloading）。调用 WordUtils.longest 时，Java 会根据你提供的参数类型知道该运行哪一个。如果给它一个 AList，它就调用 AList 的那个方法。SLList 也一样。

Java 聪明到能处理两个针对不同类型的同名方法，这很好，但重载有几个缺点：

* 极其重复，很难看，因为现在有两段几乎一模一样的代码。
* 要维护的代码更多，这意味着如果想对 `longest` 方法做一个小改动，比如修一个 bug，就得在每种列表对应的方法里都改一遍。
* 如果想再做更多种列表，就得为每个新的列表类复制一份这个方法。

## 8.2 上位词、下位词与 implements 关键字

### 上位词、下位词与接口继承

在英语以及日常生活中，词语和事物之间存在逻辑上的层级关系。

狗（dog）是所谓的贵宾犬（poodle）、阿拉斯加雪橇犬（malamute）、哈士奇（husky）等的*上位词*（hypernym）。反过来，贵宾犬、阿拉斯加雪橇犬和哈士奇是狗的*下位词*（hyponym）。

这些词构成了一个「是一个」（is-a）关系的层级：

* 贵宾犬「是一种」狗
* 狗「是一种」犬科动物
* 犬科动物「是一种」食肉动物
* 食肉动物「是一种」动物

![hierarchy](https://web.archive.org/web/2020id_/https://joshhug.gitbooks.io/hug61b/content/assets/hierarchy.png)

SLList 和 AList 也有同样的层级关系！SLList 和 AList 都是更一般的「列表」的下位词。

我们会在 Java 里把这种关系形式化：如果 SLList 是 List61B 的下位词，那么 SLList 类就是 List61B 类的**子类**（subclass），List61B 类是 SLList 类的**父类**（superclass，也叫超类）。

**图 4.1.1** ![subclass](https://web.archive.org/web/2020id_/https://joshhug.gitbooks.io/hug61b/content/assets/subclass.png)

在 Java 里，要*表达*这种层级，需要做**两件事**：

* 第 1 步：为一般的列表这个上位词定义一个类型——我们选用 List61B 这个名字。
* 第 2 步：指明 SLList 和 AList 是那个类型的下位词。

新的 List61B 就是 Java 所说的**接口**（interface）。它本质上是一份契约，规定列表必须能做什么，但不为这些行为提供任何实现。你能想到为什么吗？

下面是我们的 List61B 接口。到这里，我们完成了建立层级关系的第一步：创建一个上位词。

```java
public interface List61B<Item> {
    public void addFirst(Item x);
    public void add Last(Item y);
    public Item getFirst();
    public Item getLast();
    public Item removeLast();
    public Item get(int i);
    public void insert(Item x, int position);
    public int size();
}
```

（译注：原文代码第三行 `add Last` 中间多了一个空格，应为 `addLast`。）

现在，要完成第 2 步，需要指明 AList 和 SLList 是 List61B 类的下位词。在 Java 里，我们在类定义中定义这种关系。

我们要给

`public class AList<Item> {...}`

加上一个定义关系的词：implements。

`public class AList<Item> implements List61B<Item>{...}`

`implements List61B<Item>` 本质上是一个承诺。AList 在说：「我承诺我会拥有并定义 List61B 接口中规定的所有属性和行为。」

现在可以修改 `WordUtils` 里的 `longest` 方法，让它接收一个 List61B。因为 AList 和 SLList 都和 List61B 有「是一个」关系。

## 8.3 重写与接口继承

### 重写

我们承诺过要在 AList 和 SLList 类里实现 List61B 规定的方法，那就来实现吧。

在子类里实现所要求的函数时，在方法签名正上方加上 `@Override` 标签是有用的（在 61B 里其实是必须的）。这里我们只对一个方法这样做了。

```java
@Override
public void addFirst(Item x) {
    insert(x, 0);
}
```

值得注意的是，即使不加这个标签，你*仍然*在重写（override）这个方法。所以从技术上说，你*不是非加不可*。不过，加上这个标签能告诉编译器你打算重写这个方法，对程序员来说是一道保险。你问为什么这有帮助？嗯，这有点像有一个校对员！如果过程中出了问题，编译器会告诉你。

假设你想重写 `addLast` 方法。如果打错了字，不小心写成 `addLsat` 怎么办？如果没加 @Override 标签，你可能发现不了这个错误，这会让调试变得更困难、更痛苦。而如果加了 @Override，编译器会在程序运行之前就停下来，提示你改正错误。

### 接口继承

接口继承指的是子类继承父类所有方法（行为）的关系。就像我们在「上位词与下位词」一节中定义的 List61B 类那样，接口包含所有的方法签名，但不包含实现。由子类来真正提供这些实现。

这种继承也是跨越多代的。这意味着，如果像**图 4.1.1** 那样有一长串父类和子类的关系，AList 不仅继承 List61B 的方法，还继承它上面每一个类的方法，一直到最高的父类，也就是说 AList 继承自 Collection。

## 等号的黄金法则（GRoE）

回想我们在第一章（即第 3 章前半）介绍的等号的黄金法则。它的意思是，每当我们写赋值 `a = b` 时，就把 b 的比特复制到 a 里，并要求 b 和 a 是同一类型。不能写 `Dog b = 1` 或 `Dog b = new Cat()`，因为 1 不是 Dog，Cat 也不是。

我们试着把这条法则用到本章前面写的 `longest` 方法上。

`public static String longest(List61B<String> list)` 接收一个 List61B。我们说它也可以接收 AList 和 SLList，可既然 AList 和 List61B 是不同的类，这怎么可能呢？嗯，回想一下 AList 和 List61B 之间有「是一个」关系，这意味着 AList 应该能放进 List61B 的盒子里！

**练习 4.1.2**：你觉得下面的代码能编译吗？如果能，运行时会发生什么？

```java
public static void main(String[] args) {
    List61B<String> someList = new SLList<String>();
    someList.addFirst("elk");
}
```

可能的答案有：

* 不能编译。
* 能编译，但在 **new** 那一行出错。
* 运行时，创建一个 SLList，它的地址存在 someList 变量里，但在 someList.addFirst() 处出错，因为 List 类没有实现 addFirst。
* 运行时，创建一个 SLList，它的地址存在 someList 变量里。然后字符串「elk」被插入到 addFirst 所作用的那个 SLList 里。

## 8.4 实现继承与 default

之前，我们的接口 List61B 只有方法头，规定 List61B **应该做什么**。不过现在我们会看到，可以在 List61B 里写一些已经写好实现的方法。这些方法规定了 List61B 的下位词**怎样**表现。

要做到这一点，必须在方法签名里加上 `default` 关键字。

如果在 List61B 里定义这个方法：

```java
default public void print() {
    for (int i = 0; i < size(); i += 1) {
        System.out.print(get(i) + " ");
    }
    System.out.println();
}
```

那么实现了 List61B 的所有类都能使用这个方法！

不过，这个方法有一个小小的低效之处。你能发现吗？

对 SLList 来说，每次调用 `get` 方法都要遍历整个列表。边遍历边打印要好得多！

我们希望 SLList 以一种和接口里规定的方式不同的方式打印。为此，需要重写它。我们在 SLList 里实现这个方法：

```java
@Override
public void print() {
    for (Node p = sentinel.next; p != null; p = p.next) {
        System.out.print(p.item + " ");
    }
}
```

现在，每当我们在 SLList 上调用 print()，调用的就是这个方法，而不是 List61B 里的那个。

（译注：本节开头原文写的是「List61B 的上位词」（hypernyms），按上下文应为「下位词」，即实现了 List61B 的那些类，译文已更正。）

## 8.5 实现继承与接口继承的区别

### 接口继承与实现继承

怎样区分「接口继承」和「实现继承」？可以用下面这个简单的区分：

* 接口继承（做什么）：只说明子类能做什么。
  * 例子：所有列表都应该能打印自己，怎么打印由它们自己决定。
* 实现继承（怎么做）：告诉子类怎样实现它们的行为。
  * 例子：列表（默认情况下）应该完全按这种方式打印自己：按顺序取出每个元素，然后打印。

## 8.6 抽象数据类型

**抽象数据类型**（Abstract Data Type，ADT）只由它的操作来定义，而不由它的实现来定义。

例如，在项目 1A 里，我们开发了 `ArrayDeque` 和 `LinkedListDeque`，它们有相同的方法，但这些方法的写法非常不同。在这种情况下，我们说 `ArrayDeque` 和 `LinkedListDeque` 是 `Deque` 这个 ADT 的*实现*。

从这段描述可以看出，ADT 和接口有一定关系。从概念上说，`Deque` 是一个接口，`ArrayDeque` 和 `LinkedListDeque` 是它的实现。在代码中，为了表达这种关系，我们让 `ArrayDeque` 和 `LinkedListDeque` 类继承 `Deque` 接口。

一些常用的 ADT 有：

* 栈（Stacks）：支持后进先出地取元素的结构
  * `push(int x)`：把 x 放到栈顶
  * `int pop()`：取出栈顶的元素
* **列表**（Lists）：一组有序的元素
  * `add(int i)`：添加一个元素
  * `int get(int i)`：取下标 i 处的元素
* **集合**（Sets）：一组无序的、互不重复的元素
  * `add(int i)`：添加一个元素
  * `contains(int i)`：返回一个布尔值，表示集合是否包含这个值
* **映射**（Maps）：一组键值对
  * `put(K key, V value)`：把一个键值对放进映射
  * `V get(K key)`：取出键对应的值

注意：加粗的 ADT 是一个更大的总接口 `Collections` 的子接口。
