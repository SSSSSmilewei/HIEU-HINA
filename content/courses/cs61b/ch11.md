## 11.1 渐近分析入门

*万事总得有个开头。*

之前，我们关注的是怎样节省*编写*程序的时间。现在，我们要学习怎样最好地利用计算机的时间和内存。

可以从两个不同的角度来看编写高效程序的过程：

1. 编程成本（*到目前为止课上讲的所有内容*）
   1. 开发程序要花多长时间？
   2. 代码是否容易阅读或修改？
   3. 代码的可维护性如何？（非常重要——很大一部分成本来自维护和扩展，而不是开发！）
2. 执行成本（*从现在起课上讲的所有内容*）
   1. **时间复杂度**：程序执行要花多少时间？
   2. **空间复杂度**：程序需要多少内存？

为了让你对接下来的内容有个概念，考虑一个**有序**数组。我们的目标是判断列表中是否有重复的元素。

```java
List<Integer> example = [-3, -1, 2, 4, 4, 8, 10, 12];
```

一种**朴素的算法**是比较每一对元素。在上面的例子里，我们会把 -3 和列表中每个元素比较，然后是 -1，然后是 2，依此类推。

一种**更好的算法**是利用列表有序这一性质！不必比较每一对元素，只需要把每个元素和它旁边的元素比较。

可以看出，**朴素的算法**似乎比**更好的算法**做了多得多的不必要的、重复的工作。但它到底多做了多少？怎样量化一个程序有多高效？本章会为你提供比较各种算法效率的正式技巧和工具！

## 11.2 刻画运行时间

*衡量计算成本的技巧。*

我们希望能*刻画*前面看到的两个算法的运行时间。换句话说，我们想找出某种代理指标，来表达每个算法的整体性能。

刻画运行时间时，我们心中有两个目标：

* 刻画应该简单，但在数学上严谨。
* 如果一个算法比另一个好，刻画应该清楚地展示出这种优越性。

视频（英文）：<https://www.youtube.com/watch?ab_channel=JoshHug&v=mRn8Z46psX8>

我们把朴素的算法和更好的算法都转换成了 Java 代码。函数 dup1 对应朴素的算法，dup2 对应更好的算法。

```java
// Naïve algorithm: compare everything
public static boolean dup1(int[] A) {  
  for (int i = 0; i < A.length; i += 1) {
    for (int j = i + 1; j < A.length; j += 1) {
      if (A[i] == A[j]) {
         return true;
      }
    }
  }
  return false;
}
```

```java
// Better algorithm: compare only neighbors
public static boolean dup2(int[] A) {
  for (int i = 0; i < A.length - 1; i += 1) {
    if (A[i] == A[i + 1]) { 
      return true; 
    }
  }
  return false;
}
```

### 技巧 1

我们考虑用来刻画运行时间的第一种技巧，是用一个客户端程序直接测量以秒计的执行时间。

有几种做法：

* 用一块真的秒表（不推荐）。
* 用 Unix 内置的 `time` 命令。
* 用普林斯顿标准库，它有一个 `stopwatch` 类。

用其中任何一种方法都会看到（准确程度各不相同，取决于是否选了真秒表那条路）：随着输入规模增大，`dup1` 完成所需的时间越来越长，而 `dup2` 完成的速度大致保持不变。

看起来技巧 1 完全可以用来刻画运行时间！实验结果很容易理解，也很容易实施。然而，它有一些严重的缺点，让我们不愿把它用在所有地方：

* 可能要跑*很长*时间才能结束。
* 运行时间会因机器、编译器、输入数据等而不同。

因为这些原因，技巧 1 达不到我们刻画运行时间的目标。它简单，但在数学上不严谨。而且，机器、编译器、输入等带来的差异，意味着结果可能无法清楚地展示 `dup1` 和 `dup2` 之间的关系。

视频（英文）：<https://www.youtube.com/watch?ab_channel=JoshHug&v=fxDIy6w09fw>

### 技巧 2A

我们可以不去实际计时算法运行花了多长时间，而是数一数每个算法完成的操作总数！直观上看，执行操作较少的算法会优于另一个。可以把两个算法的输入规模 `N` 固定成一样的，比较执行的操作次数。

我们把这个方法用到输入规模为 `N=10000` 的 `dup1` 算法上：

```java
for (int i = 0; i < A.length; i += 1) {
  for (int j = i+1; j < A.length; j += 1) {
    if (A[i] == A[j]) {
       return true;
    }
  }
}
return false;
```

| 操作 | 次数（N=10000 时） |
| --- | --- |
| i = 0 | 1 |
| j = i+1 | 1（最好情况）到 10000（最坏情况） |
| < | 2 到 50,015,001 |
| += 1 | 0 到 50,005,000 |
| == | 1 到 49,995,000 |
| 数组访问 | 2 到 99,990,000 |

操作 `i = 0` 只在函数调用的最开始执行一次。`j = i+1` 复杂一些——在 `A[0] == A[1]` 的最好情况下，它只执行一次（自己确认一下这个事实！）。在最坏情况下，外层循环中 `i` 取的每个值都会初始化 `j` 一次，所以一共初始化 10000 次。

越往循环深处走，算出精确的次数就越不可行。后面我们会说明，精确的数字其实没那么重要。

总结一下技巧 2A：我们解决了*与机器无关*的问题。机器的差异（通常）不影响执行的操作总数。不过，算出每种操作的全部次数很繁琐。而且，我们选的输入规模是任意的，我们也不知道实际运行要花多少时间。

### 技巧 2B

可以改为计算*符号化的次数*（symbolic count），来解决选择输入规模的问题，也就是用输入规模 `N` 来表示次数。用这种技巧，可以更新表格，加入符号化的次数：

| 操作 | 符号化次数 | 次数（N=10000 时） |
| --- | --- | --- |
| i = 0 | 1 | 1 |
| j = i+1 | 1 到 N | 1（最好情况）到 10000（最坏情况） |
| < | 2 到 (N² + 3N + 2)/2 | 2 到 50,015,001 |
| += 1 | 0 到 (N² + N)/2 | 0 到 50,005,000 |
| == | 1 到 (N² - N)/2 | 1 到 49,995,000 |
| 数组访问 | 2 到 N²-N | 2 到 99,990,000 |

用符号化的次数，我们可以看出算法怎样随输入规模*伸缩*（scale）。不过，现在算起来更繁琐了！而且它仍然没有告诉我们实际的时间。

#### 解答

| 操作 | 符号化次数 | 次数（N=10000 时） |
| --- | --- | --- |
| i = 0 | 1 | 1 |
| j = i+1 | 0 到 $N$ | 0 到 10,000 |
| < | 0 到 $N-1$ | 0 到 9,999 |
| == | 1 到 $N-1$ | 1 到 9,999 |
| 数组访问 | 2 到 $2N-2$ | 2 到 19998 |

（译注：`dup2` 的代码里其实没有 `j = i+1` 这个操作，表中这一行沿用了原文；这里应理解为循环变量的自增 `i += 1`。）

我们来比较 `dup1` 的表格和 `dup2` 的表格：

`dup1` 的表格：

| 操作 | 符号化次数 | 次数（N=10000 时） |
| --- | --- | --- |
| i = 0 | 1 | 1 |
| j = i+1 | 1 到 $N$ | 1（最好情况）到 10000（最坏情况） |
| < | 2 到 $(N^2 + 3N + 2)/2$ | 2 到 50,015,001 |
| += 1 | 0 到 $(N^2 + N)/2$ | 0 到 50,005,000 |
| == | 1 到 $(N^2 - N)/2$ | 1 到 49,995,000 |
| 数组访问 | 2 到 $N^2-N$ | 2 到 99,990,000 |

`dup2` 的表格：

| 操作 | 符号化次数 | 次数（N=10000 时） |
| --- | --- | --- |
| i = 0 | 1 | 1 |
| j = i+1 | 0 到 $N$ | 0 到 10,000 |
| < | 0 到 $N-1$ | 0 到 9,999 |
| == | 1 到 $N-1$ | 1 到 9,999 |
| 数组访问 | 2 到 $2N-2$ | 2 到 19998 |

可以看到，在最坏情况下，`dup2` 的表现明显比 `dup1` 好！

一种解释是：`dup2` 完成和 `dup1` 同样的目标所需的操作更少。

一个更好的认识是：在最坏情况下，`dup2` 的算法伸缩性好得多（例如 $(N^2 + 3N + 2)/2$ 对比 $N$）。

一个**更好**的认识是：抛物线（$N^2$）总是比直线（$N$）增长得快。

## 11.4 渐近行为

*拿出你最好的表现！*

在大多数应用中，我们最关心 $N$ 非常大时会发生什么。这叫作*渐近行为*（asymptotic behavior）。我们想知道哪些类型的算法能处理大量数据。需要高效算法的应用举几个例子：

* 模拟几十亿个粒子之间的相互作用
* 维护一个有几十亿用户的社交网络
* 编码几十亿字节的视频数据

伸缩性好的算法，比伸缩性差的算法有更好的*渐近*运行时间行为。

视频（英文）：<https://www.youtube.com/watch?ab_channel=JoshHug&v=vxYADFsa3HU>

回到刻画 `dup` 函数运行时间的原始问题。回想一下，我们希望刻画具备以下特点：

* 简单，并且在数学上严谨。
* 清楚地展示 dup2 优于 dup1。

第二个任务我们已经完成了！我们能清楚地看到 `dup2` 的表现比 `dup1` 好。不过，我们的做法既不简单，在数学上也不严谨。幸好，可以用一系列简化来解决这些问题。

### 简化 1：只考虑最坏情况

比较算法时，我们常常只关心最坏情况。最坏情况往往是最能看出有趣效应的地方，所以通常可以忽略最坏情况以外的所有情况。

#### 例子

考虑下面某个算法的操作次数。你预计这个算法运行时间的增长阶（order of growth）是多少？

* $N$（线性）
* $N^2$（二次）
* $N^3$（三次）
* $N^6$（六次）

| 操作 | 次数 |
| --- | --- |
| 小于（<） | $100N^2 + 3N$ |
| 大于（>） | $N^3+1$ |
| 与（&&） | $5000$ |

**答案**：$N^3$（三次）

直观上看，$N^3$ 比 $N^2$ 增长得快，所以它会「占主导」。为了进一步说服你，考虑下面的论证：

* 假设 < 运算符花 $\alpha$ 纳秒，> 运算符花 $\beta$ 纳秒，&& 花 $\gamma$ 纳秒。
* 总时间是 $\alpha (100N^2 + 3)+\beta (2N^3+1)+5000\gamma$ 纳秒。
* 对非常大的 $N$，$2\beta N^3$ 这一项比其他项大得多。
* 从微积分的角度想可能有帮助。$N$ 趋于无穷大时会怎样？最后哪一项占主导？

（译注：按上面的表格，总时间应为 $\alpha (100N^2 + 3N)+\beta (N^3+1)+5000\gamma$；原文的式子和表格对不上，但不影响结论：$N^3$ 项占主导。）

### 简化 2：只关注一种操作

挑出某种有代表性的操作，作为整体运行时间的代理指标。在 `dup` 的例子里：

* 好的选择：自增 `increment`、**小于**、**等于**或**数组访问**。
* 不好的选择：**赋值** `j = i + 1`，或 `i = 0`。

我们选的这种操作叫作「**成本模型**」（cost model）。

### 简化 3：去掉低阶项

忽略低阶项。

**合理性检查**：为什么这样做讲得通？（和上面的检查点有关！）

### 简化 4：去掉乘法常数

忽略乘法常数。

* 为什么？它们没有实际意义！
* 选出单个有代表性的操作时，我们已经「扔掉」了一些信息。
* 有些操作的次数是 $3N^2$、$N^2/2$ 等等。总的来说，它们都属于 $N^2$ 这个家族、具有它的形状。

### 检查点练习

把我们的四条简化规则用到 `dup2` 的表格上。

| 操作 | 符号化次数 |
| --- | --- |
| i = 0 | 1 |
| j = i+1 | 0 到 $N$ |
| < | 0 到 $N-1$ |
| == | 1 到 $N-1$ |
| 数组访问 | 2 到 $2N-2$ |

**参考答案**：数组访问，增长阶为 $N$。

<、== 和 j=i+1 也都是不错的答案。

### 简化小结

* 只考虑最坏情况。
* 挑一种有代表性的操作（即成本模型）。
* 忽略低阶项。
* 忽略乘法常数。

## 11.5 简化的分析流程

*没那么简单。*

**（痛苦的）分析流程小结**

* 列一张所有可能操作的精确次数表（要花很多力气！）。
* 用 4 条简化规则把表格转换成最坏情况的增长阶。

现在我们提出另一种完全不用列表格的方法！

视频（英文）：<https://www.youtube.com/watch?v=lJ1A8Jyeba0&ab_channel=JoshHug>

简化的分析流程包括：

* 选择成本模型，即我们要计数的那种有代表性的操作。
* 用下面任一方法算出这种代表性操作次数的增长阶：
  * 精确计数，再丢掉不必要的部分；或者……
  * 用直觉或观察来判断增长阶。这需要靠练习积累。

#### 例子：嵌套 for 循环的分析——精确计数

求 `dup1` 最坏情况运行时间的增长阶。

```java
int N = A.length;
for (int i = 0; i < N; i += 1)
   for (int j = i + 1; j < N; j += 1)
      if (A[i] == A[j])
         return true;
return false;
```

我们选择成本模型为 *== 操作的次数*。

看循环的结构，内层循环第一次运行 N-1 次。第二次迭代时 i=1，所以内层循环再运行 N-2 次。第三次迭代时 i=2，所以内层循环再运行 N-3 次。因此循环运行的总次数是：

$$\text{cost} = 1 + 2 + 3 + \ldots + (N-2) + (N-1)$$

这个成本可以化简为 $\frac{N(N-1)}{2}$（[怎么化简？](https://en.wikipedia.org/wiki/1_%2B_2_%2B_3_%2B_4_%2B_%E2%8B%AF)）。用简化规则扔掉所有低阶项和常数，得到最坏情况的增长阶 $N^2$。

#### 例子：嵌套 for 循环的分析——几何论证

* 可以看出，等号比较的次数可以用一个直角三角形的面积表示，它的直角边长为 $N- 1$。
* 因此，面积的增长阶是 $N^2$。
* 这绝不是一眼就能看出来的。要花时间练习才能看出这些规律！

## 11.6 小结

总结本章：

* 给定一段代码，可以把它的运行时间表示成一个函数 $R(N)$。
  * $N$ 是函数输入的某个**性质**，常常表示输入的**规模**。
* 我们不去求 $R(N)$ 的精确值，只关心求出 $R(N)$ 的**增长阶**。
* 一种做法（不是万能的）：
  * 选一种有代表性的操作。
  * 设 $C(N)$ 是这种操作出现次数关于 $N$ 的函数。
  * 确定 $C(N)$ 的增长阶 $f(N)$，即 $C(N)\in \Theta(f(N))$。
  * 常常（但不总是）考虑最坏情况的次数。
  * 如果这种操作花常数时间，那么 $R(N)\in \Theta(f(N))$。

## 11.7 练习

### 事实性问题

1. 用 `N` 分析下面代码的运行时间：

```java
for (int i = 0; i < N; i++) {
    int j = 0;
    while (j < N) {
        j = N;
    }
}
```

2. 设 $f(N) = 2N$。下面哪些说法是对的？
   * [ ] $f(N) \in \Theta(1)$
   * [ ] $f(N) \in \Theta(N)$
   * [ ] $f(N) \in \Theta(N^2)$
   * [ ] $f(N) \in O(1)$
   * [ ] $f(N) \in O(N)$
   * [ ] $f(N) \in O(N^2)$

<details>

<summary>第 1 题</summary>

注意内层循环只运行一次，因为它在第一次迭代时就把 `j` 设成了 `N`。因此，运行时间就是外层循环的运行时间，外层循环迭代 `N` 次。所以总的运行时间是线性的。

</details>

<details>

<summary>第 2 题</summary>

记住 $\Theta$ 表示增长阶相同（这里是线性），而 $O$ 可以粗略地理解为「小于或等于」某个增长阶。

* [ ] $f(N) \in \Theta(1)$
* [x] $f(N) \in \Theta(N)$
* [ ] $f(N) \in \Theta(N^2)$
* [ ] $f(N) \in O(1)$
* [x] $f(N) \in O(N)$
* [x] $f(N) \in O(N^2)$

</details>

### 程序性问题

1. **判断对错。** 假设有一个函数 $f$，已知 $f(N) \in \Theta(N^2)$。如果在规模为 $N$ 的输入上运行 $f$，再在规模为 $2N$ 的输入上运行，后者大约要花 4 倍的时间。
2. **判断对错。** 假设有一个函数 $f$，已知 $f(N) \in \Theta(N^2)$。如果在规模为 100 的输入上运行 $f$，再在规模为 200 的输入上运行，后者大约要花 4 倍的时间。

<summary>第 1 题</summary>

**对**。这正是渐近的定义。

</details>

<details>

<summary>第 2 题</summary>

**错**。100 可能太小，渐近行为还没开始显现。记住，渐近只适用于非常大的输入！

### 元认知问题

1. 为什么用渐近分析而不用经验计时（例如 Lab 3 里的 `Stopwatch` 类）？

<details>

<summary>第 1 题</summary>

相比经验计时，渐近分析有几个优点。看看你能不能在下面的列表之外想出更多！

* 不同的计算机运行速度不同。取决于体系结构、硬件组件，甚至室温，同样的代码执行的经验时间可能相差很大。
* 在极大的输入上测试代码可能不可行。
* 渐近分析与语言无关。同一个算法用不同语言写，经验运行时间可能不同（例如 C 通常比 Python 快大约 10 到 400 倍），但渐近运行时间相同。
* 最坏情况的运行时间可能只在某些难以用经验方法测量的情况下出现。

</details>
