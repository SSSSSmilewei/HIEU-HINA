## 25.1 哈希表回顾与默认的哈希函数

*「关键就在于我们有一堆都很短的列表。」——Hug 教授*

我们继续理解哈希。我们已经看过集合和映射的实现：

1. 基于红黑树的做法：TreeSet / TreeMap
   * 要求元素是可比较的（有小于、大于的概念）
   * 对数时间复杂度
2. 基于哈希表的做法：HashSet / HashMap
   * 如果 hashCode 把元素分散得很好（冲突很少），操作是常数时间的

回想一下，用哈希表时，思路是：对于想存进哈希表的任何一份数据，比如一个 String（或任何别的类型的对象），我们需要把它变成一个叫作哈希码的数。所以像「Mihir」这样的字符串可以转换成 -2101281024。

> 趣闻：这个整数可以是大约负二十亿到大约二十亿之间的任何数，即所有 Java 整数的范围。这个范围大约有 40 亿个整数，即 2^32 个整数。如果你对为什么是这样感兴趣，请选修 CS 61C！

有了这个数，我们想把它转换成桶的编号（即要把这个新条目加进众多链表中的哪一个）。在第一个例子里，我们用 `Math.floorMod(x, 4)`，因为底层的桶数组长度是 4。

如果取「Mihir」转换出的哈希码 -2101281024，再对 4 取模，得到 0。这把哈希码 -2101281024 化成了一个合法的下标 0。这意味着我们会用第 0 个桶来放数据「Mihir」，把它放进第 0 个桶的链表里。

> 本质上，可以把 Java 的哈希表想成一个按桶标签分类的链表数组，希望通过利用这些链表获得更好的性能。

但应该用多少个链表（桶）？这是一个重要的问题，因为随着往桶里插入的元素越来越多，链表的长度必然会增长，这又会损害哈希表操作的运行时间。

例如，假设我们插入了「Mihir」「Mirchandani」「loves」和「61B」这样的字符串，它们的哈希码碰巧都能被 4 整除。在这种情况下，所有字符串都会被放进下标为 0 的桶，全都插进同一个链表。查找操作的运行时间会怎样？嗯，我们得把整个链表查一遍才能找到数据！这是线性时间的，太慢了，配不上 HashMap 以查找快速著称的名声。

上次我们看到，链表的数量可以是可变的。思路是：只要负载因子（N/M，其中 N 是表中的元素个数，M 是桶的个数）超过某个常数，就调整那个链表数组的大小。后面我们会看到 Java 选的是 0.75。这能防止冲突发生得太频繁。只要元素在各个桶之间分散得好，每个桶里的链表大多数都很短，这意味着平均来说我们会得到常数运行时间！

例子：如果哈希表的负载因子是 3，而 `hashCode()` 函数把条目均匀地分散开，每个桶里最终只有 3 项，查找操作花 $\Theta(1)$ 的时间。

### 比较各数据结构的运行时间！

| | contains(x) | add(x) |
| --- | --- | --- |
| 茂密的 BST | Θ(log N) | Θ(log N) |
| 不调整大小的拉链法哈希表 | Θ(N) | Θ(N) |
| 会调整大小的拉链法哈希表 | Θ(1) | Θ(1) |

## 25.2 其他哈希函数带来的分布

*HashMap / 哈希表的查找速度很快，但那项「超能力」背后是哈希函数。*

假设我们的 `hashCode()` 实现只是返回 0。

```
@Override
public int hashCode() {
    return 0;
}
```

<details>

<summary>我们预计会得到怎样的分布？</summary>

我们预计哈希表中的所有元素都会在第 0 个桶里。正如上一节讨论的，哈希表会把所有元素都放进第 0 个桶，因为 hashCode 就是这样告诉它的。第 0 个桶里会有一个包含所有数据元素的链表，查找时间是很低效的线性时间，而不是我们期望的常数时间。不管提供什么键，hashCode 总是告诉 HashMap 只往第 0 个桶里加，这就是为什么会得到这么长的链表。那么怎样确保得到常数的查找时间？用一个更好的哈希函数！

</details>

为了得到更均匀的分布，我们可以做类似于上一节那样的事，利用取模。比如说，规定哈希表有 4 个桶。这意味着它有 4 个对应的链表，4 个桶下标标为 {0, 1, 2, 3}。在 `hashCode()` 函数里不需要取模，因为哈希表会替我们做这一步，以保证能加进相应的桶。正如前面说的，哈希码其实可以是 40 亿个不同值中的任何一个整数！

通过取模，我们保证哈希码得出的数可以表示成一个下标，并明确指出要加到哪个链表。此外，一次加入一系列数时，我们会看到数在各个链表中均匀分布，从而得到常数的查找时间。

```
@Override
public int hashCode() {
    return num;
}
```

这个哈希函数应该能得到均匀得多的分布！`num` 不同的对象现在会更分散地落在各个桶里，而不是全都挤在第 0 个桶。如果我们的类没有显式地重写 `hashCode()` 函数，Java 会用默认的实现，它返回对象在内存中的地址作为哈希码！

### 为什么还要自定义哈希函数？

视频（英文）：<https://youtu.be/4_gRlDS9AMQ>

我们来讨论默认的 hashCode 函数是不是一个好的 hashCode 函数！它的分散效果其实不错，因为它依赖于不同对象住在内存中不同位置这一事实，而内存地址实际上是随机的。我们会得到好的分布，因为对象基本上被分配了随机的下标来插入哈希表。

这就引出了一个有意思的问题：既然默认的哈希码分散得很好，我们为什么还关心别的自定义哈希函数？我们会在下一节读到这个问题。

## 25.3 contains 与重复元素

### contains

#### ColoredNumber 对象的 equals() 方法

假设 ColoredNumber 的 `equals()` 方法如下，即两个 ColoredNumber 的 num 相同时它们就相等。

```java
@Override
public boolean equals(Object o) {
   if (o instanceof ColoredNumber otherCn) {
       return this.num == otherCn.num;
   }
   return false;
}
```

#### HashSet 检查 contains() 时的行为

假设 ColoredNumber 的 `equals()` 方法如上，即两个 ColoredNumber 的 num 相同时它们就相等。

```java
int N = 20;
HashSet<ColoredNumber> hs = new HashSet<>();
for (int i = 0; i < N; i += 1) {
    hs.add(new ColoredNumber(i));
}
```

假设我们现在检查 12 是否在哈希表里。

```java
ColoredNumber twelve = new ColoredNumber(12);
hs.contains(twelve); //returns true
```

> 我们**期望** `contains` 返回什么？

<summary>答案</summary>

我们期望 `contains` 调用返回 true，所有的 `12` 生而平等！

</details>

#### 用默认的哈希码查找元素

假设我们用的是默认的哈希函数（使用内存地址）：

```java
int N = 20;
HashSet<ColoredNumber> hs = new HashSet<>();
for (int i = 0; i < N; i += 1) {
   hs.add(new ColoredNumber(i));
}
ColoredNumber twelve = new ColoredNumber(12);
hs.contains(twelve); // returns ??
```

> `contains` 实际返回什么？

<details>

<summary>答案</summary>

有 5/6 的概率返回 false。

默认的 `hashCode()` 基于内存地址，equals 基于 `num`。

有两个 `num = 12` 的 ColoredNumber 对象。一个在 HashSet 里，另一个是上面的代码新创建的。

每个内存地址是随机的，它们取模后落到同一个桶的机会只有 1/6（这里的哈希表有 6 个桶）。

例子：如果上面的代码创建的 `ColoredNumber` 对象 `twelve` 在内存位置 6000000，它的 hashCode % 6 是 0。HashSet 去第 0 个桶找，找不到 12。

</details>

> 难题：如果默认的哈希码分散得很好，我们为什么还要费事创建自定义的哈希函数？

<details>

<summary>答案</summary>

为了让哈希表的操作正常工作，`equals()` 和 `hashCode()` 之间必须保持一致。

</details>

**基本规则（也是合法哈希码确定性的定义）：** 如果两个对象相等，它们**必须**有相同的哈希码，哈希表才能找到它。

### 重复的值

视频（英文）：<https://www.youtube.com/watch?index=5&list=PL8FaHk7qbOD637Q-6p7nn5dKz1tK6WAjJ&v=3HmCkRYsAGg>

#### 重写了 equals() 却没有重写 hashCode()

假设我们有同样的 `equals()` 方法（比较 `num`），但没有重写 `hashCode()`。

```java
public boolean equals(Object o) {
   ...  return this.num == otherCn.num; ...
}
```

加入 0 到 19 的结果如下：

![](https://raw.githubusercontent.com/Berkeley-CS61B/sp26-gitbook/main/.gitbook/assets/image%20%2810%29.png)

```java
ColoredNumber zero = new ColoredNumber(0);
hs.add(zero); // does another zero appear?
```

> 调用 add(zero) 时，可能发生下面哪些情况？
>
> 选项：
>
> 1. 第 0 个桶里加入一个 0。
> 2. 第 1 个桶里再加入一个 0。
> 3. 某个别的桶里加入一个 0。
> 4. 不会出现重复的零。

<details>

<summary>答案</summary>

有 3 个选项是对的：#1、#3、#4。

可能在第 0 个桶里加入一个 0，可能在某个别的桶里加入一个 0，也可能不会出现重复的零。

新的零会落到一个随机的桶里。

* 5/6 的机会：落在第 0、2、3、4 或 5 个桶里。出现重复！
* 1/6 的机会：落在第 1 个桶里（原来的那个 0 就在这个桶里），不会重复！（`equals()` 拦住了它）

</details>

### 要点：equals() 与 hashCode()

结论：如果你的类重写了 equals，也应该以一致的方式重写 hashCode。

* 如果两个对象相等，它们必须总是有相同的哈希码。

如果不这样做，一切都会出问题：

* `contains` 找不到对象（除非碰巧运气好）。
* `add` 会产生重复元素。
