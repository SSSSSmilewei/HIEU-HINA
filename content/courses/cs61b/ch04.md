## 测试与选择排序

中高级程序员能具备的最重要的技能之一，是判断自己的代码是否正确的能力。在本章里，我们会讨论怎样编写测试来评估代码的正确性。在这个过程中，我们还会讨论一种叫作选择排序的排序算法。

### 一种新的做法

你写的程序可能有错误。在课堂环境里，你对代码正确性的信心来自用户交互、代码分析和自动评分器测试的某种组合，其中最后一项在很多情况下最重要，尤其因为它是你拿分的方式。

当然，自动评分器（autograder）并不神奇。它们是课程教师写的代码，和你写的代码本质上没什么两样。在真实世界里，这些测试是由程序员自己写的，而不是由某个像 Josh Hug 那样好心的第三方来写。

在本章里，我们会探讨怎样编写自己的测试。我们的目标是创建一个名叫 `Sort` 的类，它提供一个方法 `sort(String[] x)`，以破坏性的方式（即直接修改原数组）对数组 `x` 中的字符串排序。

作为一种全新的思路，我们会先写 `testSort()`，等测试写完之后，才去写真正的排序代码。

### 临时测试

为 `Sort.sort` 写测试相对直接，只是有些繁琐。只需要构造一个输入，调用 `sort`，然后检查方法的输出是否正确。如果输出不正确，就打印第一个不匹配的地方并结束测试。例如，我们可以这样写一个测试类：

```java
public class TestSort {
    /** Tests the sort method of the Sort class. */
    public static void testSort() {
        String[] input = {"i", "have", "an", "egg"};
        String[] expected = {"an", "egg", "have", "i"};
        Sort.sort(input);
        for (int i = 0; i < input.length; i += 1) {
            if (!input[i].equals(expected[i])) {
                System.out.println("Mismatch in position " + i + ", expected: " + expected + ", but got: " + input[i] + ".");
                break;
            }
        }
    }

    public static void main(String[] args) {
        testSort();
    }
}
```

可以写一个空的 `Sort.sort` 方法来检验我们的测试，如下所示：

```java
public class Sort {
    /** Sorts strings destructively. */
    public static void sort(String[] x) {        
    }
}
```

用这个空的 `Sort.sort` 方法运行 `testSort()`，会得到：

```sh
Mismatch in position 0, expected: an, but got: i.
```

得到一条错误信息是件好事！这说明我们的测试在起作用。非常有意思的是，我们现在给自己设计了一个小游戏，目标是修改 `Sort.sort` 的代码，让这条错误信息不再出现。这有点像心理上的小把戏，但很多程序员发现，给自己出这些小谜题几乎会让人上瘾。

事实上，这很像课上有自动评分器的情形：你会发现自己一心想得到自动评分器的认可。现在你有能力为自己的代码设立一位裁判，只有把代码写对，才能赢得它的认可。

**重要提示**：你可能会问：「为什么要遍历整个数组？为什么不直接用 `==` 检查两个数组是否相等？」原因是，检验两个对象是否相等时，不能简单地用 `==` 运算符。`==` 运算符比较的是内存盒子里的原始比特，例如 `input == expected` 检验的是 `input` 和 `expected` 的地址是否相同，而不是数组里的值是否相同。所以我们在 `testSort` 里用了一个循环，并打印第一个不匹配的地方。也可以改用内置方法 `java.util.Arrays.equals`，而不用循环。

上面这一个测试工作量不算大，但写一整套这样的*临时*（ad hoc）测试会非常繁琐，因为要写一大堆不同的循环和打印语句。下一节我们会看到 Google Truth 库怎样帮我们省去很多工作。

### 用 Truth 测试

Google Truth 库提供了许多有用的方法和功能，能简化测试的编写。例如，可以把上面那个简单的*临时*测试换成：

```java
import static com.google.common.truth.Truth.assertThat;
public class TestSort {
   /** Tests the sort method of the Sort class. */
   public static void testSort() {
       String[] input = {"cows", "dwell", "above", "clouds"};
       String[] expected = {"above", "clouds", "cows", "dwell"};
       Sort.sort(input);

       assertThat(input).isEqualTo(expected);
   }

   public static void main(String[] args) {
       testSort();
   }
}

```

**这段代码简单得多**，而做的事情几乎完全一样，即如果两个数组不相等，它会告诉我们第一个不匹配的地方。例如，在一个什么也不做的 `Sort.sort` 方法上运行 `testSort()`，会得到：

```sh
Exception in thread "main" arrays first differed at element [0]; expected:<[an]> but was:<[i]>
    at org.junit.internal.ComparisonCriteria.arrayEquals(ComparisonCriteria.java:55)
    at org.junit.Assert.internalArrayEquals(Assert.java:532)
    ...
```

虽然这个输出比我们的临时测试难看一点，但本章最后会讲怎样让它更好看。

### 选择排序

在写 `Sort.sort` 方法之前，需要一个排序算法。最简单的排序算法大概就是「选择排序」了。选择排序由三步组成：

* 找到最小的元素。
* 把它移到最前面。
* 对剩下的 N-1 个元素做选择排序（不碰最前面那个元素）。

例如，假设有数组 `{6, 3, 7, 2, 8, 1}`。这个数组里最小的元素是 `1`，所以把 `1` 移到最前面。有两种自然的做法：一种是把 `1` 插到最前面，其他数依次后移，即 `{1, 6, 3, 7, 2, 8}`。不过，高效得多的做法是直接把 `1` 和原来最前面的元素（这里是 `6`）交换，得到 `{1, 3, 7, 2, 8, 6}`。

对剩下的数重复同样的过程即可，即 `... 3, 7, 2, 8, 6}` 里最小的是 `2`。把它交换到前面，得到 `{1, 2, 7, 3, 8, 6}`。一直重复，直到数组有序，依次得到 `{1, 2, 3, 7, 8, 6}`、`{1, 2, 3, 6, 8, 7}`，最后是 `{1, 2, 3, 6, 7, 8}`。

可以用最初在第 2.4 节引入的「不变式」概念，从数学上证明这个排序算法对任何数组都正确，不过本教材不做这个证明。继续之前，试着自己写一个短的数组，在上面做一遍选择排序，确保你理解了思路。

知道了选择排序的原理，就可以在空的 `Sort.sort` 方法里写几行简短的注释来引导思路：

```java
public class Sort {
    /** Sorts strings destructively. */
    public static void sort(String[] x) { 
           // find the smallest item
           // move it to the front
           // selection sort the rest (using recursion?)
    }
}
```

接下来几节，我会试着完成选择排序的实现。我会用一种和学生解题时相似的方式来做，所以**一路上会故意犯几个错误**。这些故意的错误是好事，因为它们能帮助说明测试的用处。如果你在阅读时发现了其中的错误，别担心，我们最后都会回过头来改正。

### findSmallest

最自然的起点是写一个找出列表中最小元素的方法。和 `Sort.sort` 一样，我们在完成方法之前先写测试。首先，创建一个只返回某个任意值的假 `findSmallest` 方法：

```java
public class Sort {
    /** Sorts strings destructively. */
    public static void sort(String[] x) { 
           // find the smallest item
           // move it to the front
           // selection sort the rest (using recursion?)
    }

    /** Returns the smallest string in x. */
    public static String findSmallest(String[] x) {
        return x[2];
    }
}
```

显然这不是正确的实现，但我们选择先写测试，之后再真正去想 `findSmallest` 怎么实现。借助 `org.junit` 库，给 `TestSort` 类加上这样一个测试非常容易，如下所示：

```java
public class TestSort {
   @Test
   public void testFindSmallest() {
       String[] input = {"rawr", "a", "zaza", "newway"};
       String expected = "zaza";
       String actual = Sort.findSmallest(input);
       assertThat(actual).isEqualTo(expected);
   }
}
```

和 `TestSort.testsort` 一样，接着运行 `TestSort.testFindSmallest` 方法，确认它失败。运行这个测试时，会看到它居然通过了，即什么信息也没有出现。这是因为我们碰巧把正确的返回值 `x[2]` 写死在了代码里。我们修改 `findSmallest` 方法，让它返回一个肯定不对的值：

```java
/** Returns the smallest string in x. */
public static String findSmallest(String[] x) {
    return x[3];
}
```

做了这个修改之后，运行 `TestSort.testFindSmallest`，会得到一个错误，这是好事：

```sh
Exception in thread "main" java.lang.AssertionError: expected:<[an]> but was:<[null]>
    at org.junit.Assert.failNotEquals(Assert.juava:834)
    at TestSort.testFindSmallest(TestSort.java:9)
    at TestSort.main(TestSort.java:24)
```

和前面一样，我们给自己设计了一个小游戏，现在的目标是修改 `Sort.findSmallest` 的代码，让这个错误不再出现。这个目标比让 `Sort.sort` 工作要小，可能更容易让人上瘾。

题外话：我碰巧返回了正确的值 `x[2]`，这可能显得相当刻意。不过，我录这节讲座视频时，确实无意中犯了一模一样的错误！

接下来转向真正去写 `findSmallest`。这看起来应该相对直接。如果你是 Java 新手，可能会写出这样的代码：

```java
/**  Returns the smallest string in x. */
public static String findSmallest(String[] x) {
    String smallest = x[0];
    for (int i = 0; i < x.length; i += 1) {
        if (x[i] < smallest) {
            smallest = x[i];
        }
    }
    return smallest;
}
```

不过，这会产生编译错误「< cannot be applied to 'java.lang.String'」。问题在于 Java 不允许用 < 运算符比较字符串。

编程时如果卡在这样一个容易描述的问题上，最好求助于搜索引擎。例如，可以用谷歌搜索「less than strings Java」。这样的搜索可能会找到 [这样一篇](https://stackoverflow.com/questions/5153496/how-can-i-compare-two-strings-in-java-and-define-which-of-them-is-smaller-than-t) Stack Overflow 帖子。

这个帖子下一个热门回答解释说：如果 `str1 < str2`，方法 `str1.compareTo(str2)` 返回负数；如果相等，返回 0；如果 `str1 > str2`，返回正数。

把它写进代码，可能得到：

```java
/** Returns the smallest string in x. 
  * @source Got help with string compares from https://goo.gl/a7yBU5. */
public static String findSmallest(String[] x) {
    String smallest = x[0];
    for (int i = 0; i < x.length; i += 1) {
        int cmp = x[i].compareTo(smallest);
        if (cmp < 0) {
            smallest = x[i];
        }
    }
    return smallest;
}
```

注意我们用了 `@source` 标签来注明参考来源。我举这个例子是给把 61B 当作正式课程来上的同学看的。这在真实世界里并不常见。

因为我们用的是完全没见过的语法特性，可能对 `findSmallest` 方法的正确性没什么信心。幸好我们刚才写了测试。运行一下，会看到什么也没打印，说明我们的代码很可能是对的。

可以通过增加更多测试用例来增强测试，提高我们的信心。例如，可以把 `testFindSmallest` 改成下面这样：

```java
public static void testFindSmallest() {
    String[] input = {"i", "have", "an", "egg"};
    String expected = "an";

    String actual = Sort.findSmallest(input);
    assertThat(actual).isEqualTo(expected);     

    String[] input2 = {"there", "are", "many", "pigs"};
    String expected2 = "are";

    String actual2 = Sort.findSmallest(input2);
    assertThat(actual2).isEqualTo(expected2);  
}
```

重新运行测试，看到它仍然通过。我们并不能绝对确定它是对的，但比完全没有测试时要确定得多。

### swap

看下面的 `sort` 方法，接下来要写的辅助方法是把一个元素移到最前面，我们称它为 `swap`。

```java
/** Sorts strings destructively. */
public static void sort(String[] x) { 
       // find the smallest item
       // move it to the front
       // selection sort the rest (using recursion?)
}
```

写一个 `swap` 方法非常直接，你以前大概写过。正确的实现可能是这样：

```java
public static void swap(String[] x, int a, int b) {
    String temp = x[a];
    x[a] = x[b];
    x[b] = temp;
}
```

不过，我们暂时故意引入一个错误，以便演示测试的用处。一个比较天真的程序员可能会这样写：

```java
public static void swap(String[] x, int a, int b) {    
    x[a] = x[b];
    x[b] = x[a];
}
```

借助 JUnit，为这个方法写测试相当容易。下面是一个测试的例子。注意我们也修改了 main 方法，让它调用 `testSwap`，而不是 `testFindSmallest` 或 `testSort`。

```java
public class TestSort {
    ...    

    /** Test the Sort.swap method. */
    public static void testSwap() {
        String[] input = {"i", "have", "an", "egg"};
        int a = 0;
        int b = 2;
        String[] expected = {"an", "have", "i", "egg"};

        Sort.swap(input, a, b);
        assertThat(expected).isEqualTo(input);
    }

    public static void main(String[] args) {
        testSwap();
    }
}
```

在有错的 `swap` 上运行这个测试，正如预期，会得到一个错误。

```sh
Exception in thread "main" arrays first differed in element [2]; expected:<[i]> but was:<[an]>
    at TestSort.testSwap(TestSort.java:36)
```

值得简单提一下：重要的是只调用 `testSwap`，而不要同时调用 `testSort`。例如，如果 `main` 方法像下面这样，`testSort` 一失败，整个 `main` 方法就会终止执行，`testSwap` 永远不会运行：

```java
public static void main(String[] args) {
    testSort();
    testFindSmallest();
    testSwap();
}
```

本章最后会学到一种更优雅的处理多个测试的方法，不必手动指定要运行哪些测试。

既然有了一个会失败的测试，就可以用它来帮助调试。一种办法是在 `swap` 方法里设一个断点，用 IntelliJ 的可视化调试功能。如果想了解更多调试知识、多练习调试，可以看 [Lab3](https://sp19.datastructur.es/materials/lab/lab3/lab3)。逐行单步执行代码，马上就能看清哪里出错（见视频，或自己试试），然后像本节开头那样，改成用一个临时变量来修正代码：

```java
public static void swap(String[] x, int a, int b) {
    String temp = x[a];
    x[a] = x[b];
    x[b] = temp;
}
```

重新运行测试，看到它现在通过了。

### 修改 findSmallest

方法的好几个部分都完成了，可以开始把它们拼起来，构成一个 `Sort` 方法。

```java
/** Sorts strings destructively. */
public static void sort(String[] x) { 
       // find the smallest item
       // move it to the front
       // selection sort the rest (using recursion?)
}
```

怎样使用 `findSmallest` 和 `swap` 方法是清楚的，但一用起来，我们马上就发现有点对不上：`findSmallest` 返回一个 `String`，而 `swap` 需要两个下标。

```java
/** Sorts strings destructively. */
public static void sort(String[] x) { 
       // find the smallest item
       String smallest = findSmallest(x);

       // move it to the front
       swap(x, 0, smallest);

       // selection sort the rest (using recursion?)
}
```

换句话说，`findSmallest` 本应返回最小字符串的下标，而不是字符串本身。犯这样的低级错误很正常，也很容易犯，所以如果你发现自己也这样，不必紧张。反复改进设计本来就是写代码过程的一部分。

幸好，这个新设计很容易改。只需要把 `findSmallest` 改成返回 `int`，如下所示：

```java
public static int findSmallest(String[] x) {
    int smallestIndex = 0;
    for (int i = 0; i < x.length; i += 1) {
        int cmp = x[i].compareTo(x[smallestIndex]);
        if (cmp < 0) {
            smallestIndex = i;
        }
    }
    return smallestIndex;
}
```

因为这是一个不小的改动，我们也应该更新 `testFindSmallest`，确认 `findSmallest` 仍然正确。

```java
public static void testFindSmallest() {
    String[] input = {"i", "have", "an", "egg"};
    int expected = 2;

    int actual = Sort.findSmallest(input);
    assertThat(actual).isEqualTo(expected); 

    String[] input2 = {"there", "are", "many", "pigs"};
    int expected2 = 1;

    int actual2 = Sort.findSmallest(input);
    assertThat(actual2).isEqualTo(expected2); 
}
```

修改 `TestSort` 让它运行这个测试，再运行 `TestSort.main`，看到代码通过了测试。现在修改 sort，可以填上排序算法的前两步。

（译注：上面测试的最后一部分调用的是 `Sort.findSmallest(input)`，原文如此，应为 `input2`；按原文写的话，第二个断言实际会失败，因为 `input` 中最小元素的下标是 2。）

```java
/** Sorts strings destructively. */
public static void sort(String[] x) { 
   // find the smallest item
   // move it to the front
   // selection sort the rest (using recursion?)
   int smallestIndex = findSmallest(x);
   swap(x, 0, smallestIndex);
}
```

剩下的就是想办法对其余元素做选择排序，也许可以用递归。下一节来处理这个问题。

回顾一下我们做成的事，值得注意的是：我们先写了测试，并在用这些方法做任何事之前，就借助测试建立了对它们正确性的信心。这是一个极其重要的思想，如果你决定采用它，它会让你受益良多。

### 递归辅助方法

这一节开始之前，先想想完成 `sort` 所需的递归调用该怎么写：

```java
/** Sorts strings destructively. */
public static void sort(String[] x) { 
   int smallestIndex = findSmallest(x);
   swap(x, 0, smallestIndex);
   // recursive call??
}
```

习惯了 Python 这类语言的同学，可能会想用切片记法之类的东西，例如：

```java
/** Sorts strings destructively. */
public static void sort(String[] x) { 
   int smallestIndex = findSmallest(x);
   swap(x, 0, smallestIndex);
   sort(x[1:])
}
```

然而，Java 里没有「子数组的引用」这种东西，也就是说，不能直接传递数组中下一个元素的地址。

「只需要考虑一个大数组的一部分」这个问题非常常见。一个典型的解决办法是写一个私有的辅助方法，它多一个（或多个）参数，用来划定要考虑数组的哪一部分。例如，可以写一个同样叫 `sort` 的私有辅助方法，只考虑从第 `start` 个元素开始的那些元素。

```java
/** Sorts strings destructively starting from item start. */
private static void sort(String[] x, int start) { 
    // TODO
}
```

和公有的 sort 方法不同，有了额外的参数 `start`，使用递归就相对直接了，如下所示。下一节我们会测试这个方法。

```java
/** Sorts strings destructively starting from item start. */
private static void sort(String[] x, int start) { 
   int smallestIndex = findSmallest(x);
   swap(x, start, smallestIndex);
   sort(x, start + 1);
}
```

有了辅助方法，还需要设置好最初的调用。如果把 start 设为 0，实际上就是对整个数组排序。

```java
/** Sorts strings destructively. */
public static void sort(String[] x) { 
   sort(x, 0);
}
```

想对本身不是递归结构的数据结构（例如数组）使用递归时，这种做法非常常见。

### 调试并完成 sort

运行 `testSort` 方法，马上就遇到了问题：

```sh
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: 4
    at Sort.swap(Sort.java:16)
```

用 Java 调试器可以看到，问题在于 `start` 不知怎么达到了 4。仔细单步执行代码（见上面的视频），会发现问题出在递归的 `sort` 方法里忘了写基本情形。修正很直接：

```java
/** Sorts strings destructively starting from item start. */
private static void sort(String[] x, int start) { 
   if (start == x.length) {
       return;
   }
   int smallestIndex = findSmallest(x);
   swap(x, start, smallestIndex);
   sort(x, start + 1);
}
```

再次运行这个测试，得到另一个错误：

```sh
Exception in thread "main" arrays first differed at element [0]; 
   expected<[an]> bit was:<[have]>
```

同样，审慎地使用 IntelliJ 调试器（见视频），可以找到一行结果和预期不符的代码。值得注意的是，我是在比你可能采用的更高的抽象层次上调试代码的，做法是多用「Step Over」（单步跳过）而少用「Step Into」（单步进入）。正如 lab 3 里讨论的，在更高的抽象层次上调试，可以把整个函数调用的结果和预期作比较，能省下大量时间和精力。

具体来说，我们发现对最后 3 个（共 4 个）元素排序时，在输入 `{"an", "have", "i", "egg"}` 上调用 `findSmallest` 方法，返回的是第 0 个元素（`"an"`），而不是第 3 个元素（`"egg"`）。仔细看 `findSmallest` 的定义，这个行为并不意外，因为 `findSmallest` 看的是整个数组，而不只是从位置 `start` 开始的那些元素。这种设计缺陷非常常见，写测试和用调试器是修正它们的好办法。

为了修正代码，我们修改 `findSmallest`，让它接收第二个参数 `start`，即 `findSmallest(String[] x, int start)`。这样就保证只在后面那些还没排好序的元素里找最小的。修改后的代码如下：

```java
public static int findSmallest(String[] x, int start) {
    int smallestIndex = start;
    for (int i = start; i < x.length; i += 1) {
        int cmp = x[i].compareTo(x[smallestIndex]);
        if (cmp < 0) {
            smallestIndex = i;
        }
    }
    return smallestIndex;
}
```

既然对一个构件（即 `findSmallest`）做了重大修改，就应该确认这些修改是正确的。

先修改 `testFindSmallest`，让它使用新的参数，如下所示：

```java
public static void testFindSmallest() {
    String[] input = {"i", "have", "an", "egg"};
    int expected = 2;

    int actual = Sort.findSmallest(input, 0);
    assertThat(actual).isEqualTo(expected);        

    String[] input2 = {"there", "are", "many", "pigs"};
    int expected2 = 2;

    int actual2 = Sort.findSmallest(input2, 2);
    assertThat(actual2).isEqualTo(expected2); 
}
```

然后修改 `TestSort.main`，让它运行 `testFindSmallest`。这个测试通过了，强烈表明我们对 `findSmallest` 的修改是正确的。

接着修改 `Sort.sort`，让它在 `findSmallest` 中使用新的 `start` 参数：

```java
/** Sorts strings destructively starting from item start. */
private static void sort(String[] x, int start) { 
   if (start == x.length) {
       return;
   }
   int smallestIndex = findSmallest(x, start);
   swap(x, start, smallestIndex);
   sort(x, start + 1);
}
```

然后修改 `TestSort` 让它运行 `TestSort.sort`，瞧，这个方法成功了。我们完成了！你现在已经看到了本讲开头说的那种「新做法」，本章剩下的部分会对它做一些反思。

### 对开发过程的反思

编写和调试程序时，你常常会在不同的上下文之间切换。试图在脑子里同时装下太多东西，最坏会酿成灾难，最好也只是进展缓慢。

有一套自动化测试有助于减轻这种认知负担。例如，我们写 `sort` 写到一半时，发现 `findSmallest` 有一个 bug。我们能够切换上下文去考虑 `findSmallest`，用 `testFindSmallest` 方法确认它是正确的，然后再切回 `sort`。这和一种更天真的做法形成鲜明对比：一遍又一遍地调用 `sort`，试图从整个算法的行为推断 `findSmallest` 方法是否正确。

打个比方，要检验降落伞的开伞拉绳是否好用，你可以坐上飞机、起飞、跳下去、拉绳，看降落伞会不会打开。不过，你也可以直接在地上拉一下，看会发生什么。同样，没必要借助 `sort` 来试 `findSmallest`。

本章前面提到过，测试还能让你对程序的基本构件建立信心，这样一旦出了问题，你更清楚该从哪里找起。

最后，测试让重构代码更容易。假设你决定重写 `findSmallest`，让它更快或更易读。我们可以放心地做出想要的修改，再看测试是否仍然通过。

### 测试的理念

**正确性工具一：自动评分器**

回到起点。自动评分器大概是你接触到的第一个正确性工具。我们的自动评分器其实是基于 JUnit，外加一些自定义的库。

自动评分器有一些很大的好处。也许最重要的是，它替你验证正确性，免去了自己写全部测试这项繁琐又学不到多少东西的工作。它还用诱人的分数激励你把代码写对，把评估过程变成了游戏。但这也可能适得其反：学生可能花过多的时间去追那最后几分，而这些分数其实并不会影响他们的成绩或学习。

然而，真实世界里没有自动评分器，依赖自动评分器会养成坏习惯。时不时上传代码、等自动评分器跑完，会拖累你的工作流程。「自动评分器驱动开发」（Autograder Driven Development）是这种做法的极端版本：学生写完所有代码，改掉编译错误，然后提交给自动评分器。拿到错误之后，学生可能试着改一改，到处加些打印语句，再提交。如此反复。归根结底，如果依赖自动评分器，你既掌控不了自己的工作流程，也掌控不了自己的代码。

**正确性工具二：JUnit 测试**

正如我们看到的，JUnit 测试为你打开了一个新世界。你不再依赖别人写的自动评分器，而是为程序的每个部分写测试。我们把这些部分中的每一个称为一个单元（unit）。这让你对代码的每个单元都有信心——你可以依赖它们。这也有助于减少调试时间，因为你可以一次只关注一个代码单元（常常是一个方法）。单元测试还迫使你弄清楚每个代码单元应该完成什么。

不过，单元测试也有一些缺点。首先，写全面的测试要花时间。很容易写出不完整的单元测试，给你对代码的虚假信心。而且很难为依赖其他单元的单元写测试（想想你的 `LinkedListDeque` 里的 `addFirst` 方法）。

***测试驱动开发（TDD）***

测试驱动开发（Test-Driven Development，TDD）是一种在写代码本身之前先为代码写测试的开发流程。步骤如下：

1. 确定一个新功能。
2. 为这个功能写一个单元测试。
3. 运行测试。它应该失败。
4. 写出能通过测试的代码。耶！
5. 可选：重构代码，让它更快、更整洁等等。只是现在我们有了一套应该通过的测试作为参照。

这门课不要求测试驱动开发，它也可能不合你的风格，但总的来说，单元测试绝对是个好主意。

**正确性工具三：集成测试**

单元测试很好，但我们也应该确保这些单元能正确地协同工作（[别像这张动图那样](https://media.giphy.com/media/3o7rbPDRHIHwbmcOBy/giphy.gif)）。集成测试验证各个组件能正确地相互配合。JUnit 其实也可以用来做集成测试。可以把单元测试想象成最细致入微的一层，集成测试在它之上一个抽象层次。

集成测试的难点在于，手动做很繁琐，自动化又很难。而且在较高的抽象层次上，很容易漏掉微妙或罕见的错误。

总结一下，你**绝对应该写测试，但只在测试可能有用的时候写！** 从 TDD 中得到启发，在有些情况下先写测试再写代码也会非常有帮助。
